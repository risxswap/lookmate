# 固定审查范围

先检查 `git status --short`、当前分支与 HEAD，再按用户范围选择比较方式。以下命令中的 BASE、START、END、COMMIT 是说明用变量，执行时使用已经核实的引用并按 shell 规则转义。

| 用户范围 | 对应证据 |
| --- | --- |
| 分支相对基准新增的已提交改动 | 固定基准与 HEAD 的 SHA，确定 merge-base，再比较 merge-base 到固定 HEAD；三点 diff 表达这一含义 |
| 两个指定版本的净差异 | 比较固定 START 与 END 的树；不用 merge-base 替换用户指定起点 |
| 单次提交 | 比较提交父版本与该提交；根提交用支持根提交的 diff-tree，合并提交明确比较哪个父版本 |
| 已暂存修改 | `git diff --cached`，针对 HEAD 与 index |
| 未暂存修改 | `git diff`，针对 index 与工作树 |
| 所有未提交修改 | `git diff HEAD` 查看跟踪文件净变化，并结合 status 和未跟踪文件清单读取新文件 |
| PR | 核对实际 base/head、PR diff 与本地状态，避免审查到无关分支 |

工作区混合修改时，已暂存和未暂存差异可以相互抵消；若用户要求分别审查两层，应分别检查，不能只看净差异。`git diff` 不包含未跟踪文件，使用 `git ls-files --others --exclude-standard` 列出后按范围读取，避免漏掉新增实现和测试。

用户只说“审查当前修改”且存在未提交改动时，默认包含所有未提交修改，并明确说明。干净工作区又没有基准时先定位任务上下文；仍无法确定且不同选择会改变结论时，只询问比较对象。未初始化仓库时可按明确文件或快照审查，说明无法区分历史与本次变更；不擅自初始化 Git。

空 diff、无法解析的 ref 或不可用的 PR 不能直接得到“审查通过”。说明实际问题并定位正确范围。读取文件、行号和测试必须对应被审版本；本地 HEAD 不匹配时读取固定版本内容或使用隔离快照，不能 reset、checkout 或清理用户工作区来配合审查。审查结束前检查范围内是否发生新修改，有变化则更新受影响结论或注明快照。
