# 运行记录与复审

## 保存与版本

默认将报告直接保存到项目根目录的 `docs/05-代码审查/`，目录不存在时创建；不增加周期 ID 或其他子目录。Git 与非 Git 项目使用同一规则。用户明确指定其他路径时遵从用户要求。

每轮使用 `YYYY-MM-DD-中文主题-第N轮.md` 命名，例如 `2026-10-20-订单校验-第1轮.md`。同一周期沿用日期和主题，通过轮次区分；新周期文件名冲突时增加时间或简短序号，保留既有报告。周期 ID 只作为报告字段用于关联复审。完成后向用户提供报告的绝对路径链接。用户要求不写文件时在对话保留同样信息，说明未持久化。

报告会出现在工作区变更中；审查结束时区分本次生成的报告与被审代码，避免把报告自身当作新业务改动触发复审。用户明确要求审查已有报告时仍应包含相应文档。不为报告修改 .gitignore 或自动创建提交。

记录固定 base、merge-base（适用时）、head SHA、比较方式与修改层。对于工作区内容，仅 HEAD 不足以识别快照：记录范围内 status、分层 diff 摘要及内容指纹，包括未跟踪文件；暂存层与工作树分别识别。指纹按内容计算，不能用时间戳代替。保留可用于后续比较的差异或隔离快照，避免记录无关秘密和完整环境变量；无法保留时注明复审需重建范围，不能假装已完成增量比较。

## 每轮报告字段

- 周期 ID、轮次、时间、仓库、审查模式与被审快照。
- 实际覆盖的路径、修改层、需求与规则来源；排除项及原因。
- 确认问题数，以及按严重程度排序的发现。
- 每个候选的稳定 ID、复核结论和依据；正式发现的状态。
- 验证命令、退出码、关键输出摘要及对应快照；未运行项与原因。
- 审查者和复核者是否独立、覆盖缺口、报告保存位置。

问题状态为 open、fixed、dismissed 或 unresolved。只有修复后的路径或验证证据支持时才标 fixed；dismissed 须记录反证或用户接受该行为的理由，接受风险不等于已经修复。缺少验证保留 unresolved。计数区分本轮新增与当前仍未解决，避免把修复项重复算成新增。

## 复审收敛

读取同一周期上轮报告，核实版本和范围连续性。固定分支原始基准，检查上次快照到当前快照的新差异，验证 open/unresolved 项，并追踪新增修改影响的必要调用上下文。用户要求扩大范围或版本被重写时明确重建比较关系；无法可靠增量比较时说明限制，重新检查相关范围。

用根因及受影响行为匹配稳定 ID，行号变化不产生新 ID。已经驳回的问题，只有出现新的相反证据才重开。首次遗漏的旧问题如在复审中确认，标明“前轮漏报”，不要伪装成本轮引入；严重问题照常报告。

默认一个周期最多三轮，不能通过自动新建周期绕过上限。三轮后汇总未解决 ID、证据缺口及重新设计建议，停止自动审查—修复循环；用户明确要求继续时记录该指示和新范围。

## 改进依据

流程借鉴 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) 中的独立复核与复审收敛思路，按本地技能使用场景实现。发生漏报或误报时，经用户授权将脱敏案例加入技能评测，分别记录真实缺陷命中、误报和收敛轮数；不以更多评论代表效果更好。
