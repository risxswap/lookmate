# 发现与严重程度

## 证据门槛

正式发现必须具备具体触发条件、可追踪的错误路径、实际影响及被审版本中的位置。解释现有保护为什么不足，并说明相对比较基准的关系。测试复现和完整静态推导均可作为证据；区分实际运行结果与推断。规范问题引用明确规则和违反后果，需求问题引用需求或可核实的接口契约。

每项包含稳定 ID、简短标题、严重程度、来源标签、文件及紧凑行范围、触发条件、预期与实际行为、影响、证据、最小修复方向、复核结论和状态。只给必要上下文，不堆积完整工具输出。行号从被审版本核对；不能定位的疑点留在待核实项。

复核结论：确认（证据完整）、驳回（记录反证）、待核实（写明缺少什么）。独立复核未能裁决的问题保持待核实，不靠多数票晋级。驳回项在运行记录中简记，最终报告不以候选数量充当缺陷数量。

| 等级 | 判据 |
| --- | --- |
| P0 | 无需特殊前提即可造成广泛严重破坏，需立即处理；谨慎使用 |
| P1 | 常见或明确支持路径中的严重错误、越权、数据损坏等，应优先修复 |
| P2 | 有具体影响的普通缺陷、需求遗漏或明确规范违例 |
| P3 | 有证据但影响较小的缺陷；不用于容纳风格偏好 |

严重程度由影响和触发条件决定，不把阿里“强制”直接映射为 P1。项目明确约定优先于通用设计偏好。

## 报告

开头说明确认问题总数，正文统一按严重程度排序，来源可多选正确性、需求、规范；同一根因只统计一次。用户明确要求双维报告时按要求分组，并用 ID 交叉引用避免重复计数。可选设计建议独立列出，不计入问题总数。

区分本次引入、本次暴露与历史问题。与当前范围无关的历史缺陷不混入正式清单；确需提醒的严重历史风险单列说明，不要求在本次变更中顺带重构。

结尾列实际检查、未运行项、未覆盖范围和待核实项。缺少规格写“需求符合性未完整评估”；未发现问题不等价于全部测试通过，也不构成合并批准。
