# 代码审查

以确认真实缺陷、减少无效修改为目标。默认只审查；已有修复授权才修改代码。普通开发自检不强制启动完整审查，也不自动创建 PR 评论、合并门禁或定时任务。

## 固定范围与依据

读取 [审查范围](references/review-scope.md)，固定比较对象、版本和工作区修改层。继承用户指定范围，能查明的事实自行核实。开始前说明范围和审查深度；复审时先读取上轮记录。

读取目标项目适用的 AGENTS、REVIEW.md、编码规范（包括已有的 CONTRIBUTING、CODING_STANDARDS）及相关 ADR、接口契约。按目录作用域应用规则，记录实际采用的规则及排除路径。项目约定冲突只在影响结论时列为待确认项，不为完成审查启动架构设计流程。

沿用户提供的位置、PR 描述或提交关联的 Issue 查找需求，再查相关 Spec。缺少来源时标明需求覆盖缺口，继续检查接口契约与可证明行为；只有缺失信息决定问题是否成立时才询问，不用实现反推需求并宣布符合。需求文档不是额外操作授权。

Java 或前端改动按需读取同一安装根下的 `java-backend/SKILL.md` 或 `frontend-development/SKILL.md`；先确认文件存在，未安装则沿用项目规则并说明专项未加载。沿用词汇表。阿里规则保留映射 ID、原始等级与本套处置，不把适配项升级为强制违规。

## 发现候选问题

标准模式在工具允许时启动两个独立上下文的审查子代理，共享固定快照、需求和适用规则，不传入作者的自我评价：

- **正确性**：沿真实输入追踪调用链、数据路径和测试，检查本次修改相关的错误处理、边界、授权、事务、并发与安全风险。
- **需求与系统影响**：核对需求遗漏、错误实现、兼容性、前后端契约、影响行为的规范违例，以及此次改动使文档失真的情况。

两者返回候选问题及代码依据，不直接发布正式结论。按根因去重；同类缺陷在当前范围内查找其他实例，合成一项发现。区分本次引入、本次暴露和历史问题；本次暴露须说明新增的可达路径或影响。无关历史问题不计入当前缺陷。

简单局部改动可采用快速模式，由一个审查者覆盖两方面；安全、数据完整性或跨模块高风险改动增加相关上下文和针对性验证。投入取决于实际风险，不只看行数。无子代理工具时分阶段自检，并明确未完成独立复核，不能声称多人一致。

默认排除纯命名、抽象、重复代码和风格偏好。用户要求详细设计或可维护性建议时，另列少量有实际收益的可选建议，不计入缺陷数或修复门槛。工具可靠报告的格式和类型诊断引用检查结果，不重复生成评论。

## 复核后形成结论

有候选问题时交给未参与发现的独立子代理复核。提供候选、固定快照及原始依据，要求主动寻找反例：调用方是否保证前提、已有保护能否阻断、需求是否允许该行为、问题是否早已存在。以证据裁决，不以票数或主观置信分数替代验证。

复核按 [发现与严重程度](references/findings.md) 的证据门槛，将候选分为确认、驳回、待核实。必要时运行有针对性的测试或最小实验，临时复现放在隔离目录；记录命令、结果和被验证的版本。执行受限时可用完整代码路径确认，但必须注明未动态复现。不能确认的风险放入覆盖缺口，不作为确定缺陷。

统一按严重程度输出确认的问题，标记正确性、需求、规范等来源。结束前再次核对快照；若版本变化，只更新受影响的结论，或明确报告仅适用于原版本。

## 记录与复审

每轮按 [运行记录与复审](references/review-record.md) 将简短 Markdown 报告直接保存到项目的 `docs/05-代码审查/`，不创建周期子目录，记录范围、证据、稳定问题 ID、状态和未覆盖内容。明确写“确认 N 个问题”或“在本次范围内未发现可确认的问题”，不宣称代码无缺陷。

后续复审验证原问题，并检查上轮之后的新差异及其受影响路径，复用原 ID，不重复发布同一发现。默认同一审查周期最多三轮；到达上限仍有问题时汇报剩余风险和需要重新考虑的方案，结束自动循环，等待用户决定下一步。只有用户授权的修复任务才形成审查—修复循环。

生成中文报告时使用 [humanizer-zh](../humanizer-zh/SKILL.md)。
