# 记录与实现对接

## 轻量记录

沿用项目已有文档位置；没有对应资料时，有内容才创建，不提前生成空文件。

创建或更新这些资料时，按 [项目文档组织](../../development-workflow/references/documentation-layout.md) 区分长期模块需求与单次变更，遵循日期命名及状态规则。

- **词汇表**：保存已确定的业务术语、含义与概念关系；没有现成位置时使用 `GLOSSARY.md`。不放任务进度、实施细节或操作验收条件。
- **Issue / Spec**：保存本次需求、状态流转、业务约束和验收条件。沿用相关任务或需求文档，不把同一规则再复制进词汇表。
- **ADR**：重要技术决定及用户要求记录的决策，按 [项目文档组织](../../development-workflow/references/documentation-layout.md) 的 ADR 落盘检查创建或更新实际文件；普通命名或业务规则保留在词汇表或 Spec 中。

术语明确后，在本轮授权范围内及时更新词汇表；尚未确定的选择留在需求讨论中。开发、诊断和审查读取同一份资料，不另建交接文档。只讨论且未授权写文件时，在回复中给出建议内容。

变更现有定义时检查受影响的文档、接口字段、枚举、页面文案和测试。若业务说明与代码冲突，分别记录预期与现状、依据和影响；先确认哪一项应改变，不静默改文档迁就代码，也不全仓重命名。

## 实现对接

按项目 `AGENTS.md` 确定的位置对接业务定义。下面仅为项目已采用 MVC 与 Vue 时的示例，不要求其他架构迁移：

| 位置 | 使用建模结论 |
| --- | --- |
| Controller 与 DTO/VO | 采用明确的输入、响应和业务术语，保持公共契约兼容 |
| Service | 实现状态校验、业务约束、操作编排和事务边界 |
| Mapper/Repository 与 Entity | 按实际查询、持久化和约束需要实现数据结构 |
| 前端界面 | 使用一致状态文案、操作可用性与失败反馈 |
| 测试 | 从已确定的业务场景构造成功、拒绝与边界预期 |

只有当前任务需要实现时，按需读取 `java-backend` 或 `frontend-development`。继承当前范围，不重复启动建模或规划。已有 Service 结构可以承载规则，建模不会自动增加 Domain 层或 Interface/Impl 配对。

本轮只梳理业务时，技术位置仅列为影响清单，不创建实体、迁移或生产代码。表结构、事务策略等技术方案不能由对象关系图自动推导为已确认决定。

Java 后端与前端专项随安装场景提供，属于可选路由。需要该专项时，先检查同一安装根下的 `<技能名>/SKILL.md` 是否存在；存在再读取，未安装时沿用项目规范并说明专项未加载，不把它当公共配套损坏，也不自动安装。
