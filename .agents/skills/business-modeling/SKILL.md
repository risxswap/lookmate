# 业务建模

目标是把当前任务的业务含义讲清楚。实现沿用项目已确认的架构，业务建模不决定技术分层或增加类层次。业务对象是概念，不自动对应 Java 类或数据库表。


项目的 `AGENTS.md` 缺少架构或技术栈定义，或定义与实现冲突时，读取 [项目约定](../development-workflow/references/project-conventions.md)，先调查、再与用户确认，沿用当前任务模式。

## 进入与范围

读取目标项目约束、已有词汇表（如 `GLOSSARY.md`）、相关 Issue / Spec、ADR 及代码。只读取术语并沿用，不等于需要重新建模。若概念、状态和约束已经明确，直接引用现有定义并返回当前任务，不创建额外文档或问答。

识别本轮是讨论、维护业务文档还是已授权实施。建模本身不扩大授权：只讨论时给出定义建议；已授权维护文档时写回对应位置；实施任务中的建模结论作为原任务输入，不重新申请相同授权。直接调用不自动启动 Java 或前端开发或整套需求流程。

## 澄清与校验

1. 找出影响当前任务的歧义，如一个词有两种含义、不同名字表示同一概念、状态定义冲突。核实实际代码、页面和数据含义，标注它们是实现事实还是业务决定；代码不自动成为预期规则。
2. 根据问题选择 [业务定义与场景](references/business-definitions.md) 中的术语、关系、状态或约束表达，只整理必要部分。
3. 用具体场景检验定义，包括相关失败、重复或部分操作。场景是待讨论例子，不是新增需求。能从材料查明的事实自行确认，只有会改变业务结果的未决选择才向用户提问，并说明建议及影响。
4. 将已明确、拟议和待确认内容分开。答案缺失时保留未知项，不默认批准，不凭猜测决定金额、权限或数据归属；继续不依赖该决定的调查。
5. 按 [记录与实现对接](references/documentation-and-mvc.md) 保存获准记录的结论，检查术语和状态是否自洽，再返回当前开发、诊断或审查任务。

## 完成条件

当前范围内会改变实现的术语、关系、状态和约束已明确，或逐项标注未决问题及其影响；已确定规则能用具体输入和结果解释，文档与代码差异有记录。只有影响该规则的未知项解决后，依赖它的实现才能按确定规则推进；不追求一次建模整个系统。

交付说明已确定定义、未决项、实际更新位置以及受影响代码/接口/页面/测试；未执行的实现或验证不能写成完成。中文文档使用 [humanizer-zh](../humanizer-zh/SKILL.md) 校订，保持术语与状态稳定。

本套参考上游领域建模方法并收窄为业务概念梳理，见 [来源与适配](references/provenance.md)。
