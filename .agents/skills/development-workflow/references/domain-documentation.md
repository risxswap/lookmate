# 记录与实现对接

## 领域模型文档

讨论收尾、用户表达阶段性认可或准备进入技术设计时，将已有结论自动写入目标项目的领域模型文档，无需用户再说一次“整理成文档”。部分问题未决也可保存草案，逐项标明影响；零散探索且尚无可归纳结论时继续讨论。用户明确要求不写文件、仅回复草稿或只读时，在回复中交付。

先查找现有业务定义并更新对应位置；项目没有约定时使用 `docs/01-项目总览/02-领域模型.md`。按业务模块组织整体定义，已有定义直接引用。内容过多时拆为 `docs/01-项目总览/02-领域模型/`，内部用编号加中文模块名命名并维护导航。文档保持稳定路径，记录最后更新日期。

按当前范围记录术语及边界、对象关系与归属、生命周期、状态流转、业务约束，以及检验规则的具体场景。保留必要的决策理由，区分已确认结论、拟议方案、假设和未决项，不抄录聊天过程。对象关系不自动等于数据库表、代码类或已确认技术设计。

- **领域模型**：维护完整业务定义和规则，作为后续需求与实现的引用依据。
- **词汇表**：如项目已有词汇表，保留简短定义与领域文档链接，不重复维护完整规则；无需另建词汇表副本。
- **需求 / Spec**：记录角色、目标、业务流程、范围和验收场景，引用领域规则；单次变更记录拟议差异，长期有效定义归入领域文档。需求整理按 [需求与缺陷](requirements-and-bugfixes.md) 处理。
- **ADR**：需要保留理由的重要技术决定按 [项目约定](project-conventions.md) 记录；普通命名和业务规则保留在领域或需求文档中。

保存草案不代表用户已确认，已确认也不代表已实现或已验证。调整已确认定义时明确标记拟议差异，保留现行规则；确认后同步有效定义，必要时链接历史变更。若业务说明与代码冲突，分别记录预期与现状、依据和影响，不静默改文档迁就代码。

变更定义时检查受影响的文档、接口字段、枚举、页面文案和测试，仅在已有实施授权内修改代码。开发、诊断和审查读取同一份资料，不另建交接文档。

交付前核对文档实际存在、覆盖本轮定义与未决项、状态与讨论一致、引用可解析；在已有导航中补充链接，没有导航时可创建简短的 `docs/README.md`。报告实际位置与剩余问题，回复摘要不能替代应保存的文件。

## 实现对接

按项目 `AGENTS.md` 确定的位置对接业务定义。下面仅为项目已采用 MVC 与 Vue 时的示例，不要求其他架构迁移：

| 位置 | 使用建模结论 |
| --- | --- |
| Controller 与 DTO/VO | 采用明确的输入、响应和业务术语，保持公共契约兼容 |
| Service | 实现状态校验、业务约束、操作编排和事务边界 |
| Mapper/Repository 与 Entity | 按实际查询、持久化和约束需要实现数据结构 |
| 前端界面 | 使用一致状态文案、操作可用性与失败反馈 |
| 测试 | 从已确定的业务场景构造成功、拒绝与边界预期 |

只有当前任务需要实现时，按需读取 `java-backend` 或 `frontend-development`。继承当前范围，不重复启动建模或规划。已有 Service 结构可以承载规则，建模不会自动增加 Domain 层或 Interface/Impl 配对。

本轮只梳理业务时，技术位置仅列为影响清单，不创建实体、迁移或生产代码。表结构、事务策略等技术方案不能由对象关系图自动推导为已确认决定。

Java 后端与前端专项随安装场景提供，属于可选路由。需要该专项时，先检查同一安装根下的 `<技能名>/SKILL.md` 是否存在；存在再读取，未安装时沿用项目规范并说明专项未加载，不把它当公共配套损坏，也不自动安装。
