# 需求与缺陷

## 澄清边界

先查项目事实：已有权限模型、接口调用方、构建命令和同类实现由 Agent 调查。技术细节能在既有约束内合理决定时，直接选择并在有影响时说明理由。

未确定的业务规则、资源权限、不可兼容的接口或数据变更，以及会扩大范围的决定，若存在多种结果且会改变用户预期，应先澄清受影响部分。提问说明具体选择及影响；答案未到时继续不依赖它的工作，不把等待超时当成确认。

已有规格和本轮授权足以决定时，按当前阶段继续规划或实施。可逆、低影响的细节可以采用明确假设；不得靠假设决定资金计算、数据归属或破坏性迁移。业务讨论形成阶段性结论后，按下文整理需求文档并保存未决项，不因为方案已写完自动实现。

## 记录粒度

新增或调整预期行为记入需求文档，实际行为偏离已确定预期记入 BUG 修复记录。局部修改沿用已有相关记录；无行为变化的内部整理无需新建文档。每项需求或 BUG 默认用一份文档容纳说明与验证，内容较多时再拆分，不预建空文件；有对应 Spec 的实施计划按下述规则单独保存。

规格至少说明触发操作、用户可见结果、关键失败条件、权限、契约变化和不在本次范围的事项。有对应 Spec 且已获实施授权时，按 [实施计划与子 agent 执行](implementation-planning.md) 先保存独立 Plan，再由子 agent 执行；同一决定只维护一处。沿用已有确认与授权，发现实质冲突时报告影响并澄清冲突部分，继续独立工作。

## 整理需求规格

业务讨论收尾、用户表达阶段性认可或准备进入技术设计时，自动汇总已有结论并保存需求草案，无需用户单独要求落盘。部分问题未决不妨碍整理；零散探索且尚无可归纳结论时继续讨论。用户要求“整理成规格”或“记录刚才的方案”时同样沿用已有讨论，不重新访谈。先定位现有需求和相关 Spec，结合领域定义、ADR 和必要代码事实。新需求和独立的需求调整各自形成需求记录，引用现行领域规则及相关历史需求；同一需求的后续讨论更新原记录。用户指定整理某份 Spec 时更新该文件。用户明确要求不写文件、仅回复草稿或只读时直接回复，不写文件。

按内容需要整理以下项目，篇幅与需求规模相称，不强制长用户故事列表或空章节：

- 问题与目标：哪些角色在什么场景下遇到问题，希望获得什么结果。
- 预期行为：业务流程、触发条件、成功结果及已明确的失败、权限和状态规则；完整领域定义由 [业务建模](domain-modeling.md) 维护，此处引用。
- 已定决定：已确认的接口、数据和实现选择，引用已有定义，不复制整份词汇表或 ADR。
- 验证方式：可观察的验收结果、已商定的测试范围及可复用的现有测试；计划执行与实际通过分开描述。
- 范围与未决项：明确不包含什么，以及尚未决定的内容及影响。

区分用户已确认决定、代码现状和未采纳建议；讨论过不等于批准。冲突或缺失先如实列出，允许交付含未决项的草稿，不为完成模板补造需求或将当前实现当成预期。已明确问题不重复提问；只有连整理对象都无法确定时才澄清该对象。

写完对照原讨论检查遗漏、扩大范围和确定程度，再按 humanizer-zh 校订中文。写文件的任务按下文完成需求落盘检查，标明实际文件位置和剩余未决项。整理完成不表示规格已获批准，不自动拆实施计划、修改业务代码、创建或更新远程 Issue；用户明确要求的后续动作另按已有授权执行。

### 从技术设计同步需求

新项目和已有项目的架构、数据库讨论每次形成阶段性结论时，检查其中的功能范围、业务流程、数据归属、权限、状态、生命周期和约束，以及已明确的性能、可靠性等验收要求。将新增或调整的预期行为按上述规则同步到对应 Spec，已有需求继续更新原记录；无需等待整套设计完成或获得编码授权。仅涉及技术选型、索引或物理表结构等实现细节且未改变预期行为时，维护设计文档即可，不按表逐一创建需求。

Spec 记录预期行为、范围和可观察的验收条件，引用架构、数据库和领域文档中的详细定义。只提取讨论已有依据的要求；表结构不能作为补造业务流程或认定需求已确认的依据。缺少验收条件时标为未决项，仍保存已明确的内容。

确认状态与实现状态分别记录：未确认结论保存为草案，列明假设和未决项；已确认内容依据代码现状标为待实现、部分实现或已实现，无法核实的实现状态注明待核实。按下文规则将已确认能力同步到功能总览。保存 Spec、确认需求和授权实施分别判断。

## 需求落盘检查

沿用目标项目现有需求位置；没有约定时使用 `docs/02-需求文档/YYYY-MM-DD-中文主题/01-需求说明.md`，不再另建模块需求与 changes 两套资料。每项需求记录背景与目标、范围、业务规则、验收条件和未决项，引用项目总览中的共用定义。讨论收尾时实际保存草案；用户只指定整理某份 Spec 时更新该文件，不扩展整套资料。

新项目及新增功能在编码前保存当前实施范围。有对应 Spec 的实施计划必须独立保存，位置和内容按 [实施计划与子 agent 执行](implementation-planning.md) 处理，需求说明以链接引用。验证记录可以保留在需求说明内，内容较多时拆为同目录的 `03-验证记录.md`，避免重复维护。仅整理需求不自动生成实施计划或验证结果。

目录日期取创建当天的用户当地日期，同一需求跨天推进保留原名，正文记录最后更新日期；独立后续需求新建目录并链接历史。草案与已确认状态、实现状态及验证结果分别记录，不用拟议变化覆盖当前有效定义。

实施完成后保存该需求的最终范围和验证证据，同步受影响的功能总览、领域模型、架构及数据库设计；共用规则以链接引用。历史需求保留当时范围与结果，后续替代通过链接说明，不要求补齐全项目历史。

交付前检查文件实际存在、覆盖需求和验收条件、状态与会话一致、引用可解析。在已有导航中链接实际文件，没有导航时创建简短的 `docs/README.md`。报告实际路径及未决项，回复摘要不能替代文件。

需求确认后，按 [功能总览](feature-overview.md) 将已确认能力及待实现范围同步到项目总览；尚未确认的草案不进入正式功能条目。用户仅要求整理指定 Spec 时保持该范围。

## BUG 修复记录

沿用项目现有缺陷记录位置；没有约定时使用 `docs/03-BUG修复/YYYY-MM-DD-中文主题/01-问题说明.md`。日期取用户当地创建日期，后续排查与修复更新同一记录，不因跨天更名。同一问题已有记录时直接更新，避免重复建档。

默认在问题说明内记录以下内容，复杂问题再拆出同目录的 `02-修复方案.md` 和 `03-验证记录.md`：

- **问题说明**：现象、影响范围、环境与版本、触发条件、复现步骤、预期及依据、实际结果、日志或其他证据。
- **修复方案**：根因及证据、修复措施、受影响位置与兼容性；未确认根因标为假设。
- **验证记录**：原问题复现证据、修复后结果、相关回归检查，以及未验证项与原因。

诊断形成阶段性结论或完成修复时实际保存记录；只有定位授权时记录结论及建议，不修改业务代码。明确要求不写文件、仅回复或只读时在回复中交付。无法复现或验证时保留证据缺口，不把猜测写成根因或宣称修复完成。

修复影响行为时补充能捕获原故障的回归检查，记录修复前失败、修复后成功的实际证据；未运行则明确说明。交付前检查记录存在、状态真实、链接有效，并更新文档导航及受影响的功能总览。无语义修正不为覆盖率添加测试。

排查发现预期行为需要新增或调整时，转入需求记录，问题说明链接对应需求；需求文档反向引用问题，不重复维护同一方案。需求确认和修复授权分别沿用当前任务范围。

## 变更边界

局部修复保持已有框架、目录和公共接口。确需改变依赖、模型或接口时列出调用方影响。已确认的架构约定按 [项目约定](project-conventions.md) 记录，并区分目标与当前实现；描述实现现状的架构文档需有代码依据，拟议设计留在任务规格中。存量不符合本套默认规则不构成整仓迁移授权。
