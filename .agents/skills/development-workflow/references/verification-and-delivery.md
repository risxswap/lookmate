# 验证与交付

## 开始前定义证据

在切片实现前说明应观察到的结果和检查方式，确认所需环境、数据和命令是否可用。检查对应用户行为和相关失败条件，例如取消成功后状态变化、重复取消不重复释放库存；不要只写“编译通过”或“接口已添加”。发现验证依赖缺失时尽早说明，继续可独立执行的工作。

## 状态与推进

| 状态 | 使用条件 |
| --- | --- |
| 待实施 | 行为已明确，代码尚未完成 |
| 实现中 | 仍有本片必要实现未完成 |
| 已实现，待验证 | 代码完成，但必要检查尚未执行或环境不可用 |
| 验证失败 | 检查已执行，结果不符合预期；记录具体失败 |
| 已验证 | 本片预先定义的必要检查通过，证据可核对 |

这些状态表达事实，不要求安装状态管理工具或机械地维护额外表格。依赖前一片的步骤以其必要证据为前提；遇到失败先定位，不能通过删断言或降低业务预期变成通过。无关既有失败单独记录，判断其是否影响本片证据。

整体完成前对照验收条件核对所有切片及其衔接，尤其是共享状态、跨片权限和失败恢复。检查范围内有新修改时重跑受影响验证；没有新增变化或疑点时不重复已通过检查。已实现但缺少必要验证的部分明确交付为未验证，不称全部验收通过。

## 验证方式

先从构建文件、包脚本和 CI 获取项目真实命令，再运行受影响范围的检查。编译证明语法和依赖可用，单测证明隔离逻辑，数据集成测试证明真实持久化行为，浏览器验证证明界面交互；分别记录，不能相互替代。

对事务、授权、并发和契约边界使用可观察结果验证，不以注解存在或文本匹配作为正确证据。复用已有测试设施，不为小修改引入另一套框架或设定任意覆盖率门槛。

涉及环境数据的验证使用隔离测试库和测试账号；运行前识别目标环境与副作用。发布、生产迁移或外部系统写入依照已有用户授权及执行环境要求处理，开发授权不自动扩展这些操作。

交付说明包含行为变化、关键文件、实际命令与结果、未运行项及原因。服务不可用、依赖缺失或浏览器不可用时明确标记未验证，不生成虚构通过记录。既有失败与本次引入失败分开说明。

涉及业务需求变化时按 [需求与缺陷](requirements-and-bugfixes.md) 更新对应需求记录；领域定义变化时按 [业务建模的记录规则](domain-documentation.md) 同步领域模型；架构抽象、数据库或重要技术决定变化时按 [实施中的设计同步](project-conventions.md#实施中的设计同步) 更新项目总览及相关决策记录，并完成代码与文档的一致性检查。修复 BUG 时按 [需求与缺陷](requirements-and-bugfixes.md) 保存问题、根因、方案和回归证据。保留需求或 BUG 记录的最终状态和验证证据，核对实际文件、内容、确认与实现状态及导航链接。

功能新增、扩展或移除时，按 [功能总览](feature-overview.md) 更新受影响条目的实际范围、实现状态和验证情况；核对代码依据，不将交付计划或编译通过写成业务能力已验证。
