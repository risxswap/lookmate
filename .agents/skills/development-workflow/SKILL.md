# 开发流程

先读取目标项目的 AGENTS.md、README、已有词汇表、相关 Issue / Spec、ADR 与构建配置。保留已有修改，沿用已确认的项目决定。架构或技术栈未在适用的 `AGENTS.md` 中说明，或约定与代码冲突时，按 [项目约定](references/project-conventions.md) 处理：已有项目先分析实现，再与用户沟通确认；新项目引导选择，确认后按授权写入 `AGENTS.md`。

## 先确定任务模式

| 用户意图 | 本轮工作与完成条件 |
| --- | --- |
| 讨论、比较、设计方案 | 调查事实，说明方案、取舍和未决问题；需求、领域或技术设计形成阶段性结论后按对应参考保存草案，实施仍按用户授权执行 |
| 整理成规格、记录已讨论方案 | 按 [需求与缺陷](references/requirements-and-bugfixes.md) 的“整理需求规格”汇总已有结论，更新或创建 Spec；不自动实施或发布 Issue |
| 梳理已有和待实现能力 | 按 [功能总览](references/feature-overview.md) 核对代码与已确认需求，保存功能范围、实现状态和验证情况 |
| 开发、修复、重构 | 在已授权范围实施并验证；保持重构的既有行为或落实明确的新行为 |
| 诊断、定位原因 | 按方法技能取得证据；仅定位时不修改业务代码，已授权修复时继续实施 |
| 审查、review | 固定代码范围并报告发现与缺口；已有修复授权才应用修改 |

从当前请求和已有授权判断模式，不要求用户每次选择。混合任务可分段执行，例如先审查再修复；“按照方案实施”可承接前文已确定的范围，不重新询问。讨论、仅整理规格或功能总览和只审查模式跳过下面的实施步骤，完成相应产出后交付。

## 按任务加载设计参考

- 业务目标、流程、范围或验收条件需要梳理，或架构、数据库讨论形成涉及预期行为的阶段性结论时，读取 [需求与缺陷](references/requirements-and-bugfixes.md)，同步需求 Spec。
- 术语、对象关系、状态或业务约束存在歧义或变化时，读取 [领域建模](references/domain-modeling.md)。
- 新项目设计，或现有项目的架构、数据库及重要技术取舍发生变化时，读取 [技术设计与项目约定](references/project-conventions.md)。
- 页面结构、视觉方向、设计规范或界面改版涉及设计决策时，按下文可选专项规则读取 `frontend-development` 的设计分支，沿用当前讨论或实施阶段。

按当前任务进入相应阶段，无对应 Spec 且规则明确的局部修改直接实施；已有结论以引用衔接，领域对象不直接推导为表或代码类。讨论形成阶段性结论后保存草案，明确要求不写文件或只读时在回复中交付。保存、确认、实施及验证状态分别记录。

## 开发执行

从零开始的新项目，先按 [项目约定](references/project-conventions.md) 的“新项目架构讨论”完成讨论，用户确认整体架构和数据库设计后，再搭建项目与编码。沿用已有确认；现有项目新增功能或较大业务模块不触发此流程。

1. 识别预期行为、受影响模块、现状和验收条件。缺陷先建立失败证据；需求中的未知行为不能用当前代码代替。
2. 业务术语、对象关系、状态或约束存在歧义或发生变化时，按需读取 [领域建模](references/domain-modeling.md)；规则明确的 CRUD 无需额外建模，继续后续实施步骤。按 [需求与缺陷](references/requirements-and-bugfixes.md) 处理会改变业务结果的未知项并决定记录粒度。继承已有决定和授权，不重复申请已获授权的开发步骤。
3. 涉及跨层字段或接口时读取 [契约协作](references/api-contract-collaboration.md)，确定成功、失败和兼容性，再修改两端。
4. 有对应 Spec 的实施，必须先按 [实施计划与子 agent 执行](references/implementation-planning.md) 保存独立 Plan，再由子 agent 按任务实现；主 agent 负责规划、协调、审查和验证，不直接写实现代码。无对应 Spec 的局部修改作为一个切片，无需额外计划文件；多步骤或跨层功能按 [行为切片](references/behavior-slices.md) 划分可验证的任务。
5. Java 实现或审查读取 `java-backend`；前端实现或审查读取 `frontend-development`。混合任务分别读取必要分支，纯后端或纯前端任务不加载另一专项。
6. 每片按 [验证与交付](references/verification-and-delivery.md) 核对证据，再推进依赖它的步骤；实现中调整架构抽象时，按 [实施中的设计同步](references/project-conventions.md#实施中的设计同步) 更新项目总览。最后检查相关跨片行为和文档一致性，并报告结果和缺口。

专项已读取本流程时，沿用当前阶段，不循环路由。配套文件缺失时报告具体路径，继续不依赖它的事实调查，不自动安装依赖或复制另一套规范。

本流程按项目架构组织开发，不预设框架、分层或部署形态。安装目录和业务源码目录相互独立；操作命令在目标项目执行。

## 文档产出

目标项目已有文档约定时沿用，不自动迁移或重命名；没有约定时使用以下编号与中文命名。`README.md` 保留为导航入口，有实际内容才创建对应目录和文件：

```text
docs/
├── README.md
├── 01-项目总览/
│   ├── 01-功能总览.md
│   ├── 02-领域模型.md
│   ├── 03-架构设计.md
│   └── 04-数据库设计.md
├── 02-需求文档/
│   └── YYYY-MM-DD-中文主题/
│       ├── 01-需求说明.md
│       └── 02-实施计划.md
├── 03-BUG修复/
│   └── YYYY-MM-DD-中文主题/
│       └── 01-问题说明.md
├── 04-技术决策/
│   └── YYYY-MM-DD-中文主题.md
└── 05-代码审查/
    └── YYYY-MM-DD-中文主题-第N轮.md
```

总览持续维护整体设计与代码能力，保持固定路径；需求和 BUG 记录各次工作的范围、方案与结果。已有 Spec 获授权实施后，按 [实施计划与子 agent 执行](references/implementation-planning.md) 创建独立计划；仅整理规格时不创建计划。需求、缺陷的拆分规则见 [需求与缺陷](references/requirements-and-bugfixes.md)，编号表示顺序，日期表示记录创建时间。

业务需求讨论形成阶段性结论、进入实施或维护需求时，按 [需求与缺陷](references/requirements-and-bugfixes.md) 保存和更新需求文档；领域定义按 [领域建模](references/domain-modeling.md) 维护；架构、数据库和重要技术决策按 [项目约定](references/project-conventions.md) 记录。保存草案、业务确认和实施授权分别判断，沿用会话中已有决定。

需求确认、功能交付或用户要求梳理项目能力时，按 [功能总览](references/feature-overview.md) 维护已实现和待实现能力；默认使用目标项目的 `docs/01-项目总览/01-功能总览.md`，沿用已有位置。

## 中文文档

生成或修改中文规格、计划、架构说明、README、技能文档或交付报告时，读取配套 [humanizer-zh](../humanizer-zh/SKILL.md)，先按事实起草，再校订本轮文字。润色不得改变规则等级、技术约束、代码、路径、授权、证据和完成状态。纯代码任务不额外启动文档润色。

## 方法技能

要求定位根因、复杂故障、偶发问题或性能回退时，读取 [diagnosing-bugs](../diagnosing-bugs/SKILL.md)；无对应 Spec、简单且原因明确的修复保留轻量路径。用户要求审查分支、PR、提交或当前修改时，读取 [code-review](../code-review/SKILL.md)，保持只审查范围，除非已有修复授权。方法技能与 Java 与前端规则配合使用，继承当前阶段，不循环启动流程；普通开发自检不强制完整审查会话。

Java 后端与前端专项随安装场景提供，属于可选路由。需要该专项时，先检查同一安装根下的 `<技能名>/SKILL.md` 是否存在；存在再读取，未安装时沿用项目规范并说明专项未加载，不把它当公共配套损坏，也不自动安装。
