# 中文用例与测试地图

生成、维护或校验正式用例时读取。正文定义执行语义，所属类型地图定义业务分类，机器目录由两者派生。临时验证不采用本格式。

## 路径与资产根

新资产使用下列布局；只建立任务涉及的类型。已有资产沿用明确的位置，历史计划和运行不搬迁、不改写。

```text
docs/
├── plan/YYYY-MM-DD-<topic>.md
├── plan/YYYY-MM-DD-<topic>-map.md
└── testing/
    ├── 00-data/01-sources/01-requirements/
    ├── 00-data/01-sources/02-openapi/
    ├── 00-data/02-analysis/
    ├── 00-data/04-catalogs/
    ├── 01-cases/01-api/00-接口测试用例.md
    ├── 01-cases/02-ui-integration/00-UI测试用例.md
    ├── 02-checks/
    ├── 04-runs/<RunId>/
    ├── 05-reports/<RunId>/
    └── 06-bugs/{01-pending-fix,02-pending-verification,03-verified}/
```

显式记录资产根 `asset_root`、用例根和实际地图路径。资产根用于解析 Wikilink，和项目根、用例根可以不同；沿用用户指定值或项目约定，新项目默认选项目根并注明这是本次配置。无需查找 Obsidian 注册信息、安装软件或插件。若计划图也使用 Wikilink，选择包含计划及用例的共同根，例如项目根或其 `docs/`；已有更窄资产根保持原约定，计划与图可用普通相对 Markdown 链接。

Wikilink 从资产根计算，省略 `.md`，例如 `[[docs/testing/01-cases/01-api/01-预约管理#^case-api-book-001|API-BOOK-001]]`。若资产根为 `docs/testing/`，相应路径从 `01-cases/` 起。不用相对于地图文件的路径，不模糊搜索同名文件；链接目标、软链接和输出须在相应资产边界内。静态校验通过只证明格式与链接可解析，未实际操作 Obsidian 时不声称渲染或点击验收。

## 文档与身份

按已有领域术语和稳定职责组织模块；跨领域场景归入主要被验证规则所属领域，辅助动作不另建重复用例。分类影响预期且无法核实时询问；普通命名和布局选择由 Agent 处理。每个模块文件容纳相关用例，使用 `<两位编号>-<中文模块名称>.md`，编号后的名称与一级标题一致，各类型独立编号。

文档顺序为非空一级标题、所属类型地图入口、可选 `## 公共准备`、`## 用例`。API 入口别名为 `返回接口测试用例`，UI 为 `返回 UI 测试用例`。正文不再维护分类树或数量表。用例结构示意如下，演示名称与字段不构成真实业务来源：

```markdown
### API-BOOK-001｜员工创建有效预约

用例编号：API-BOOK-001 ^case-api-book-001

优先级：P1
状态：草拟
关联需求：REQ-BOOK-001
关联风险：RISK-BOOK-001
关联接口：createBooking
```

CaseId 使用大写英文、数字、连字符，全集合唯一且跨移动、重排稳定。标题使用全角 `｜`，编号独占段落，块标识为 `case-` 加小写 CaseId；三者一致。相邻用例用独占行 `---` 分隔，首尾不加分隔线。`优先级` 为 P0～P3，`状态` 为草拟／可执行／已废弃。关联编号用 `、` 分隔。

无需求编号时写 `来源：契约`、`来源：回归` 或 `来源：探索`，并用非空 `来源依据` 定位文档及操作、BUG 或探索记录。有需求编号时机器目录使用“需求”来源。API 必须以 `关联接口` 填写唯一主 operationId；辅助准备和查询不改变主接口身份。来源不足的假设保留在分析中，不伪造需求编号。

## 步骤与数据

每条用例的分区为 `#### 准备`、可选 `#### 数据`、`#### 步骤`、可选 `#### 最终检查`、可选 `#### 清理`，分区不重复。步骤从 1 连续编号，每步有非空 `操作：`，用一项或多项 `检查：` 给出可观察判定；同层字段缩进一致，可统一加列表前缀。纯准备步骤可以把判定留在后续，但整条用例至少有一项检查。

按需添加 `观察：`（对象、证据通道、观察区间）、`等待：`（终止条件、预算及来源）、`并发：`（独立参与者、同步点、汇合与重试约定）、`保存为：`（单项输出）。没有产品时限时记录测试等待预算，不把预算写成产品承诺。按来源区分缺失字段、空字符串、空白和 null；数据表不隐含循环，多组独立执行分别建用例。

具名数据在数据或公共准备中写为 `- 名称：定义`，通过 `「名称」` 引用。公共准备只有被用例明确写出 `满足“公共准备”` 时生效。步骤输出使用 `保存为：资源编号 ← 本步响应的 id 字段`，多输出分行，声明后才能使用；同一作用域不重复、循环或提前引用。代码围栏和引号包裹的展示文案按字面值处理。关键身份、状态和预期须能从用例及明确引用中确定。

步骤明确使用 API 或页面途径，定位器和认证材料放执行适配层。失败后停止依赖失败结果的动作，保留安全核查、证据与适用清理。仅完成操作不能证明检查通过；当前响应也不能作为独立预期。

## 相应类型地图

API 正式用例需 API 地图，UI 正式用例需 UI 地图；另一类型没有用例时不要求其地图。存在某类用例却缺少对应地图必须修复，不靠缩小扫描范围隐藏。地图模板为 [API](../assets/templates/api-test-map.md) 和 [UI](../assets/templates/ui-test-map.md)，初始只有空根。

地图采用 `mindmap-plugin: basic` frontmatter 和唯一类型根标题 `# 接口测试用例` 或 `# UI 测试用例`，按“业务领域 → 业务功能 → 业务规则／测试条件 → 用例”组织实际分类列表；领域也可用二级标题。无说明、图例、表格、占位业务节点或其他元数据。

```markdown
---
mindmap-plugin: basic
---

# 接口测试用例

- 会议预约
  - 创建预约
    - 有效输入
      - 🟠 草拟｜员工创建有效预约｜[[docs/testing/01-cases/01-api/01-预约管理#^case-api-book-001|API-BOOK-001]]
```

以上为合成语法示例。每条正文用例在所属类型地图中恰有一个主叶子，已废弃用例也保留。叶子的一行依次为状态、短标题和末尾编号链接，只有编号使用 Wikilink，别名必须为 CaseId，叶子无子节点。正文入口须返回所属地图。校验拒绝遗漏、重复、跨类型、块身份不一致、失效目标和越界链接。

| 正文状态 | 地图状态 | 含义 |
| --- | --- | --- |
| 草拟 | 🟠 草拟 | 尚未满足准入 |
| 可执行 | 🔵 可执行 | 可进入正式计划，不表示运行通过 |
| 已废弃 | ⚪ 已废弃 | 保留追溯，不进入新计划 |

草拟属性可成对填写 `处理提示` 和 `处理依据`。提示只取待独立评审／待修订／待复核／待澄清，依据须定位真实记录。地图同步为 `🟠 草拟 · 待独立评审｜短标题｜[[路径#^case-id|CaseId]]`；没有正文提示时地图不猜测。有多项缺口时提示当前依赖，其余保留评审记录。切到可执行或已废弃时移除当前提示属性，历史记录保留。地图不叠加运行通过或失败状态。

## 校验、目录与指纹

下列命令从目标项目根执行，`<技能目录>` 指已安装的 testing-workflow，参数相对于命令工作目录。初始化仅用于需要创建正式资产的项目：

```sh
python3 <技能目录>/scripts/init_testing.py . --types api
python3 <技能目录>/scripts/validate_cases.py docs/testing/01-cases --asset-root . --json
python3 <技能目录>/scripts/build_catalog.py docs/testing/01-cases --asset-root .
```

`--types` 可取 api、ui、all，默认 all。初始化保留已有地图、用例和历史运行，不推导缺失分类，不建立旧的 `docs/testing/03-plans/`。`PATH` 可传项目根、docs、testing 或完整用例根；明确使用完整用例根可以避开旧新布局探测歧义，但不能漏掉另一类型现有用例。地图有非默认位置时按类型显式传 `--api-map FILE` 或 `--ui-map FILE`。`--vault-root` 是 `--asset-root` 的兼容别名，不代表依赖 Obsidian。

校验只读，失败时先处理具体文件、行号和路径，不用生成目录掩盖问题。目录成功默认写到 `docs/testing/00-data/04-catalogs/case-catalog.json`，校验失败不覆盖现有目录。自定义 `--output` 仍须位于相应 `00-data/04-catalogs/`。核对工具返回的真实用例根、资产根和地图集合。

Schema v5 的稳定字段如下：

- 顶层 `schema_version: 5`、`case_format: chinese-markdown-v2`、资产根相对 `cases_root`、`maps`（实际存在类型的路径及 SHA-256）、`documents`（用例根相对路径及 SHA-256）、`cases`。
- 逐例 `case_id`、`case_revision`、`title`、`case_type`、`priority`、`lifecycle_status`、`requirement_ids`、`risk_ids`、`source_kind`、`source_reference`、`operation_id`、`source_file`、`source_line`、`anchor`、`classification_path`；可选 `draft_hint`、`draft_hint_source`。
- `case_type` 为接口测试／UI 集成测试；`source_kind` 为需求／契约／回归／探索；`source_file` 相对用例根，`source_line` 为一基行号，`anchor` 无 `^`，分类取地图祖先节点。输出稳定排序，不人为编辑派生目录。

`CaseRevision` 为规范化执行语义的 SHA-256，显示为 `h-` 加 12 位十六进制：包含生效准备、输入、操作与检查、等待／观察／并发／输出、最终检查、清理和主 operationId；排除名称、编号展示、锚点、优先级、生命周期、处理提示、需求风险元数据、分类和路径。措辞变化也可能改指纹，哈希不证明语义等价。文档与地图原始哈希另行冻结集合来源。

结构校验不能代替 [语义与独立评审](coverage-challenge-review.md)。语义变化需复核受影响计划，历史运行继续使用原快照。使用 [API 用例模板](../../api-testing/assets/templates/api-test-case.md) 或 [UI 用例模板](../../ui-testing/assets/templates/ui-integration-test-case.md) 时替换合成来源、业务规则、数据及链接，再生成地图与评审；模板不是真实测试证据。
