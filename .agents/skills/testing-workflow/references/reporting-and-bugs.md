# 报告与 BUG 复验

正式运行使用本页汇总，字段、状态和结论策略以 [运行契约](run-data-contract.md) 为唯一结构定义。临时验证直接交付原始记录与必要证据，可记录已确认缺陷，但不伪造正式运行身份。

## 事实与失败分析

`manifest.json` 冻结计划、用例来源、环境和版本；`results.jsonl` 保存逐场景、逐 Attempt 的执行事实。首次失败、实际结果、执行器和证据不得被后续通过覆盖。后续分析可追加失败分类、BUG ID 和依据，保留原记录与变更来由。

失败分类为产品缺陷、用例缺陷、自动化脚本问题、环境问题、测试数据问题、接口文档问题、待分析。断言失败先核对预期来源、数据和执行方式；确认产品行为偏离明确预期才记产品缺陷。来源不足或证据不能定位时保持待分析或相应文档问题，不猜测内部根因。源码诊断交给开发流程，接口和 UI 的外部证据边界继续有效。

## 同源报告

正式运行收尾后用 `generate_report.py --manifest FILE --results FILE --output-dir DIR` 输出 `docs/testing/05-reports/<RunId>/report.html` 与 `report.md`，命令见运行契约。报告是派生视图，可重新生成；先修正有事实依据的输入问题，不分别手工修改 HTML 和 Markdown 的统计。

生成前核对所有计划场景都有真实结果，未开始的明确记 NotExecuted，并保留全部尝试。输入无法从真实记录补全时交付缺口；报错时保留原文件，修复后重新生成。没有建立 RunId 的准备阶段不生成空报告。

新运行声明 `testing-workflow-v1`：任何确认产品失败优先判 Failed，待分析失败或必测缺口判 Blocked，仅非必测缺口可 PassedWithRisk，全部要求满足才 Passed。历史策略按运行契约显示并保留，不为升级报告改写历史语义。报告成功不表示测试通过，单场景状态也不被总体结论覆盖。

统计与范围同时展示：总数为五种最终状态之和；通过率为 Passed / (Passed + Failed)；执行完成率为 (Passed + Failed + Blocked + Skipped) / 总数。需求及接口覆盖分子采用最终 Passed 或 Failed 对应的需求／operationId，分母来自 Manifest 明确范围。显示分母与未验证项，分母为零时标不可计算，不用单一百分比代替结论。

检查 HTML 可读、Markdown 来自同一事实、失败和缺口可定位、证据路径能访问。交付以 HTML 为主要入口并附 Markdown，说明执行器及版本、实际环境与覆盖范围。Agent 浏览器通过不算 Playwright 自动化覆盖；另一工具的诊断不替换原运行。脱敏在持久化前完成，报告隐藏样式不能替代脱敏。

## 本地 BUG

使用 [BUG 模板](../assets/templates/bug.md)，在三个同级目录按稳定 ID 定位：

| 目录 | 含义 |
| --- | --- |
| `docs/testing/06-bugs/01-pending-fix/` | 待修复 |
| `docs/testing/06-bugs/02-pending-verification/` | 已有修复反馈，待验证 |
| `docs/testing/06-bugs/03-verified/` | 验证要求满足 |

文件名为 `BUG-NNN-简短名称.md`，BUG ID 稳定不复用，目录是状态事实源，正文不另放状态字段。结果只引用稳定 BUG ID，不依赖会移动的路径。建立前检索三个目录去重；确认可复现产品缺陷后才新建，偶发或预期不明的观察先留在分析与运行记录。

BUG 写清版本、环境、前提、最小复现操作、来源支持的预期、实际和证据，足以独立复现。正式发现关联 RunId 和 CaseId，证据引用对应运行，不复制附件；临时发现引用检查记录与证据，RunId/CaseId 留为不适用，不补造身份。

在授权内将 BUG ID 关联结果并重生成报告。本技能不自动发送外部消息或接入缺陷系统。需要修复时提供记录给开发流程；独立测试仓库和业务仓库都可以使用，不规定研发必须在另一个仓库工作。

## 修复反馈与验证

收到实际修复版本、构建和验证环境后，按已授权任务追加反馈并移入待验证目录。用户只提供反馈而没有请求执行时可完成记录，到执行仍遵守入口授权范围；已有复验授权不重复询问。

正式复验使用新计划和新 RunId，Manifest 保存原运行、原版本和原尝试摘要，并分开组织直接验证、影响回归和关键链路回归。从原失败、变更影响、共享状态／权限／数据及历史高风险点选择相关场景，每项写明选择理由；排除项说明缺口。临时发现需要正式复验时先转换为经评审的正式用例，原检查记录继续作为来源，不伪造旧 RunId。

将本轮结果追加到 BUG 验证记录，并按结论处理：

| 结论 | 条件与动作 |
| --- | --- |
| Verified | 直接验证及计划回归满足、版本匹配且证据完整，移到已验证 |
| PartiallyVerified | 直接验证通过，回归仍有非产品失败或未完成项，留待验证 |
| NotFixed | 直接验证确认原产品问题仍在，移回待修复 |
| RegressionFound | 直接验证通过，回归确认相关产品问题，移回待修复并分析是否另建 BUG |
| CannotVerify | 直接验证受其他失败、环境、数据或版本等影响，留待验证 |

新策略的缺陷验证结论按验证分组检查全部尝试中的产品／待分析失败，再检查最新结果；历史策略只按最新结果与分类回放。整体批次结论单独按运行策略计算。移动为已验证前同时核对本轮不存在未处置相关产品失败或待分析失败，不用分组的最终通过掩盖历史尝试问题。报告展示原运行和新运行，修复后通过不改写原失败。

原发现仅有临时检查记录时，正式运行可用常规 Manifest 关联 BUG，在 BUG 验证表记录来源与各组结果；没有真实原 RunId 就不填要求原运行摘要的 `verification` 对象。保持证据链，不为套用报告特性伪造历史。
