# 缺陷诊断

先确认用户要求仅定位还是同时修复，继承已有范围与授权。读取目标项目约束、故障相关实现及现有测试。预期行为依据需求或用户说明，不能把当前代码当预期。直接进入时按需读取公共 [需求与缺陷](../development-workflow/references/requirements-and-bugfixes.md)，不重新启动规划。

进入任务时读取已有词汇表（如 `GLOSSARY.md`）、相关 Issue / Spec 和 ADR，沿用业务术语与已确定取舍；资料缺失不要求补齐整套文档。


项目的 `AGENTS.md` 缺少架构或技术栈定义，或定义与实现冲突时，读取 [项目约定](../development-workflow/references/project-conventions.md)，先调查、再与用户确认，沿用当前任务模式。

## 证据循环

1. 记录触发输入、实际结果、预期结果、环境与版本，区分观测事实和猜测。选择能够捕获该症状的检查：失败测试、请求重放、浏览器操作或最小运行程序。先运行一次并保留脱敏结果，确认不是环境故障造成的另一种失败。
2. 尽量缩小复现范围，缩短运行时间。每次删减重跑检查，避免最小化后丢掉原始问题。简单且原因明确的错误可直接建立失败检查并修复，不强制列多项假设。
3. 复杂问题列出有证据支持的候选原因及可证伪预测，按可能性和验证成本排序；数量由实际问题决定。一次改变一个关键变量，用针对性日志、断点或实验区分原因。
4. 仅在授权包含修复时修改实现。对相关 Java 或前端规则，分别按需读取 `java-backend` 或 `frontend-development`，技术专项转回公共流程时保留本轮诊断状态。
5. 用能捕获原问题的检查证明修复前失败、修复后通过，再验证原始完整场景及受影响边界。删除本轮临时探针，保留有维护价值的回归测试；不要清理用户原有日志或文件。

偶发、并发和性能问题读取 [特殊诊断场景](references/diagnostic-cases.md)。无法复现时可继续静态分析并标注候选原因，说明缺少的证据；不能将候选原因写成已确认根因，或仅凭代码修改宣称修复有效。

## 交付

诊断形成阶段性结论或完成修复时，按公共 [BUG 修复记录](../development-workflow/references/requirements-and-bugfixes.md) 保存问题、根因证据、方案与验证结果；明确要求只读或不写文件时在回复中交付。

说明症状、实际复现命令及结果、哪些假设被排除、根因证据、变更和回归结果。只定位的任务交付结论和修复建议，不自动改业务代码。无法验证时给出具体缺口；测试运行要求沿用公共 [验证与交付](../development-workflow/references/verification-and-delivery.md)。生成中文诊断文档时使用 [humanizer-zh](../humanizer-zh/SKILL.md)，保留证据与不确定性。

Java 后端与前端专项随安装场景提供，属于可选路由。需要该专项时，先检查同一安装根下的 `<技能名>/SKILL.md` 是否存在；存在再读取，未安装时沿用项目规范并说明专项未加载，不把它当公共配套损坏，也不自动安装。
