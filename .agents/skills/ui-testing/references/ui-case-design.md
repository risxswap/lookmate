# UI 覆盖展开

生成、补充或实质修订正式 UI 用例时，与公共 [覆盖设计](../../testing-workflow/references/test-case-design.md) 一起使用。专业交互评审也按本表检查。范围、来源和准入沿用公共规则。

## 从需求展开条件

1. 按业务功能提取来源条款、目标角色、测试条件和可观察业务结果。项目有 spec 时读取其设计稿与交互说明的具体版本；没有对应设计或文字说明时先保留业务条件，实际入口、控件名称和操作路径待核实，不套用示例步骤。
2. 对每个功能逐项检查下表，记录适用条件及覆盖节点；不适用项说明依据。来源要求检查但缺少预期的条件记为待澄清，执行手段或数据缺失记为阻塞，不能为了清空缺口直接排除。
3. 输入用等价类和边界值，字段联动用决策表，页面生命周期用状态转换表。状态表记录起始状态、触发动作、目标状态、页面反馈及业务结果；覆盖来源规定的允许与禁止转换，不枚举所有理论组合。
4. 按明确失败机制组合高风险条件，例如“提交尚未完成时再次点击”或“切换筛选后旧响应晚到”。写明涉及的规则、操作顺序和可观察后果；缺少故障语义时提出待澄清项。设计场景不等于授权故障注入或环境改动。
5. 按下一节勘察页面，再将条件细化为独立用例，映射 CaseId 和具体检查位置。同一用例可覆盖多个条件，但条件之间需要不同前提、操作或独立结论时拆分，不能把多个数据值藏在一条用例中隐式循环。

## 页面勘察与来源记录

分别记录需求依据、设计依据和实页观察：需求与已确认设计定义正确结果；观察用于核实当前页面、定位和操作路径。设计稿、交互说明冲突时定位受影响预期，按已有确认核实，仍不明确的列为待澄清。页面表现与明确预期不同则保留差异，按失败分析处理，不修改预期迎合实现。

按功能和角色在真实浏览器中查看入口、控件、关键状态及跳转，记录实际操作和可达范围。可复用已有 Trace、录屏、截图及交互记录，但须核对应用版本、角色、相关功能开关和路径仍适用；过期或覆盖不足时补查受影响部分。静态截图只证明对应画面，不能单独证明加载、校验、返回、异步恢复等动态路径。测试源码和定位器只供适配，不能替代实页观察。

使用公共覆盖设计模板的页面观察栏记录页面地址、应用版本或构建标识、观察时间、角色、浏览器及相关环境、来源方式、关键操作与实际状态、脱敏证据位置和待核实项，再关联覆盖节点或 CaseId。记录放在本轮 `docs/testing/00-data/02-analysis/`，证据可引用已存在的合法位置或保存在该分析记录的同名目录；未进行正式运行时不伪造 RunId 或运行通过结果。

勘察沿用已有授权。只获准设计用例时，使用已有证据和获准的页面访问、非破坏性交互；创建、提交、删除、发送通知及故障注入须有对应授权。缺少权限、环境或账号时记录受影响的待核实路径，继续独立部分，不以“勘察”为由执行未授权业务操作。无需勘察整个应用后才生成用例，可逐功能推进。

| 当前依据 | 可交付内容 | 准入处理 |
| --- | --- | --- |
| 只有需求，缺少交互依据和实页观察 | 业务测试条件、预期与交互待决项 | 不编造具体 UI 步骤；未形成用例的条件保留分析台账 |
| 有已确认设计或文字交互说明，实页尚未核实 | 标明操作来自设计的用例草稿 | 关键路径待实页核实，保持草拟 |
| 有适用版本的实页观察及明确预期 | 按已核实路径细化的 UI 用例 | 通过独立评审和其余准入检查后可执行 |

实页核实不要求测试预期已经通过。已观察到预期入口缺失时，可以从已核实可达的页面编写“应显示该入口”的检查并记录差异；需要该入口才能继续的后续路径单独标记未核实，不能虚构已到达的弹窗或页面。已知产品失败与用例未核实分别记录。

## 逐功能覆盖表

下表是查找条件的提示，不自动新增产品要求。按公共覆盖设计模板记录适用性及映射，无需再建一份 UI 台账。

| UI 维度 | 展开条件 | 需要落实的检查 |
| --- | --- | --- |
| 角色与入口 | 相关角色、菜单入口、直接链接、登录失效后的访问 | 到达的页面、可见与可操作内容、返回目标及已声明的访问规则 |
| 表单与输入 | 必填、空串与空白、已声明边界、格式、字段联动、纠错和输入保留 | 错误位置与内容、提交条件、关联字段和纠错后的状态；UI 无法输入的协议值分配给 API |
| 页面状态 | 初始、加载、空数据、成功、校验错误、服务错误、禁用及切换 | 展示内容、可用动作、错误解除和最终状态；加载结束有可观察终点 |
| 操作与导航 | 提交、取消、重复点击、刷新、前进后退、离开后重入 | 操作次数、页面与地址状态、数据保留或清除、取消后的禁止副作用 |
| 异步与恢复 | 慢响应、失败重试、响应乱序、提交结果不确定 | 当前操作对应的反馈、旧结果处理、恢复后的数据及是否重复写入；只使用已确认语义 |
| 业务链路与数据 | 列表到详情、编辑后返回、跨页面同步、刷新后持久化、集合为 0／1／多项 | 本次记录标识与关键字段一致、数量与顺序符合来源；成功提示不能代替持久化检查 |
| 权限与隔离 | 操作入口、越权访问反馈、资源归属、权限变更和切换身份 | 可观察的访问结果与残留数据；按钮隐藏不证明接口已拒绝越权，接口权限另分配 API 检查 |
| 适配与可访问性 | 项目要求的视口、浏览器、键盘、焦点、语言及视觉标准 | 对应环境中的可操作性与已确认呈现要求；任务不要求的专项检查记录排除依据 |

## 从条件写成可执行用例

每条用例明确角色与登录态、入口、初始数据和隔离标识、唯一操作顺序、逐步页面检查、最终业务结果及清理。异步断言写可观察终点和有限预算；“未发送请求”“没有新增记录”等否定断言写观察起点、窗口、查询范围和结束条件。预算可引用执行计划，来源未定义的业务时限不能用执行预算代替。

操作必须能到达目标条件。要求按钮禁用的场景应检查禁用状态及适用的禁止副作用；需要验证重复点击时说明按钮在什么状态可操作，不能强行点击被禁用控件冒充用户路径。无法构造的故障或状态记录限制，不以跳过或直接调用接口算作 UI 已覆盖。接口辅助准备、查询和清理按 [页面执行](ui-execution.md) 处理。

在用例准备中引用页面观察记录及覆盖本用例关键路径的具体证据；正文使用已核实的用户可见名称和操作顺序，定位器放执行适配层。准入时核对证据版本与适用范围，未核实路径保持草拟并定位缺口。已有用例也核对当前路径依据是否适用，只补查受影响部分，不追补历史生成评审。

对重要规则推演最小错误，定位能发现它的检查。例如来源要求预约提交后可在“我的预约”查看：只检查成功提示会放过“提示成功但未保存”，应重新进入或刷新后核对本次记录及字段；若来源还要求防止重复创建，再补查记录唯一性。示例只说明断言方法，不新增预约规则。

## 交给独立评审

按公共 [独立挑战评审](../../testing-workflow/references/coverage-challenge-review.md) 分工：业务覆盖评审核对来源、角色与链路，专业交互评审核对本表条件、状态转换及页面路径证据，断言与可执行性评审检查反例、观察、数据和清理。各评审者先读需求、已确认设计和不含生成者结论的原始页面证据，形成自己的清单，再对照覆盖设计和用例；页面证据不足时列具体缺口或在授权内补查。

设计结束时能从每条相关规则和适用维度定位到用例检查或有据处置，关键转换及高风险组合有明确映射，评审发现完成必要复核。待澄清、阻塞和排除项单列，不计作已覆盖；结论只针对本轮已确认范围。
