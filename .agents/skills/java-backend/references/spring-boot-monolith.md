# Spring Boot 单体实践

本页仅适用于项目已确认采用 Spring Boot 单体的情况，不作为新项目默认选型。沿用项目约定的模块边界与职责；项目采用 MVC 时，可按以下职责组织：Controller → Service → Mapper/Repository → 数据库，业务规则与事务由 Service 承担。业务建模用于明确概念和规则，不要求聚合根、领域服务、仓储抽象或事件总线。模块通过清晰接口交互，不因单体共享数据库而随意绕过其他业务模块规则。

Controller 负责协议、校验和响应映射，业务服务确定业务操作与事务边界，持久层负责存储。对外 DTO 与持久化实体按暴露字段和生命周期区分，避免直接序列化实体关联或允许客户端写入内部权限字段。

接口用于真实多实现、模块边界或替换需求；单一 Service 不强制配套 Interface/Impl。构造器注入显式依赖，发现循环依赖先检查职责，避免用延迟注入长期掩盖设计问题。

配置沿用项目提供机制，按环境区分并校验必要值；密钥由环境或既有秘密管理机制注入，不写入源码或日志。遵守目标版本的配置优先级，不自造集团覆盖顺序。新依赖尽量沿用项目依赖管理，核对兼容性后添加。

异常在既有统一出口映射为稳定业务错误或服务错误；响应不暴露堆栈和数据库细节。日志保留可排查的请求关联信息。仅在需要时增加健康检查，避免把内部敏感配置暴露为公共诊断端点。

修改事务逻辑继续读取 [持久化与事务](persistence-and-transactions.md)。启动、关闭或线程资源变化检查资源生命周期和异常退出行为。
