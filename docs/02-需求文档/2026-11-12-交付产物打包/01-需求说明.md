## 已确认范围

- 增加 package.sh 打包交付产物，各组件使用独立 Docker Compose，已有运行时镜像挂载程序产物启动。
- 交付包包含中间件部署配置，不只包含应用程序。
- server 与 web 部署在同一台机器，HTTPS 由直接运行在宿主机上的已有 Nginx 承接。
- 部署服务器可以拉取运行时镜像，不需要离线镜像 tar 或 docker load 流程。

本次按已讨论的 MySQL、Redis 同机方案提供默认部署配置，连接地址仍保留配置能力。范围为 server、web、MySQL、Redis、frp 调试配置和 ops 显式迁移入口。小程序交付包和 deploy.sh 自动部署保留为后续范围。实际验证采用本地构建与隔离检查。

## 目标与现状

构建端生成可拷贝到部署机器的交付包，部署机器使用已有运行时镜像启动构建产物。部署时无需重新编译业务源码。

实施前 `tools/package.sh` 支持 `server|web|all`：server 执行 Maven verify，web 执行 npm ci 和生产构建；当时尚未归集交付目录或生成压缩包。实施前仓库已有 MySQL、Redis 和 frp 的独立 Compose，server/web 的 Compose 由本次补齐。

沿用[架构设计](../../01-项目总览/03-架构设计.md#docker-compose-部署)：各应用与基础设施独立维护 Compose、配置和运行目录；Java 后端由已有运行时镜像挂载程序，Web 由 Nginx 挂载静态文件；构建打包与部署分开，Flyway 由 ops 显式执行，应用只检查结构兼容性。

## 实施范围与交付行为

扩展现有 `tools/package.sh`，根目录 `package.sh` 作为转发入口。目标支持 `server|web|infra|all`，默认 all；支持 `--version` 与 `--output`。server 包含后端和配套 ops，web 仅包含 Web，infra 仅归集 MySQL/Redis 配置，all 包含以上全部组件。默认输出为 `output/packages/`，未指定版本时使用 UTC 时间。

各组件分别交付：

- server 交付可执行 `lookmate-server.jar`、独立 `docker-compose.yml`、配置模板及说明。使用固定版本的 Java 21 运行时镜像，通过只读挂载加载 JAR 和配置。
- web 交付生产静态目录、独立 `docker-compose.yml`、Nginx 配置及配置模板。使用固定版本的 Nginx 镜像，通过只读挂载加载静态资源和配置。
- infra/mysql 与 infra/redis 交付各自独立生产 Compose、配置、环境模板及说明，沿用现有中间件目录。源码新增生产文件，保留原开发配置；打包时将生产文件归集为标准的 docker-compose.yml 与 .env.example。frp 保持开发调试用途。
- ops 随 server/all 交付 V1–V11 SQL、一次性 Flyway Compose、环境模板及只接受 info/validate/migrate 的执行脚本。MySQL Connector/J9.7.0 从同包后端 JAR 提取，单文件只读挂载，部署时不编译或下载 Maven 依赖。
- 小程序、运营端、frp 不纳入本次交付包。

生成 `lookmate-<版本>-<目标>.tar.gz` 与外部 `.sha256`，包内附交付说明、BUILD-INFO.properties 和 SHA256SUMS。构建信息记录版本、目标、UTC时间、Git提交及工作区状态。交付目录保留 apps/server、apps/web、infra/mysql、infra/redis、ops 的职责，每个组件独立 Compose，不提供合并全部组件的总 Compose。

各组件安装在稳定目录，应用产物放各自 `releases/<版本>/`，通过 LOOKMATE_VERSION 选择。实际配置、日志、生成结果暂存与数据库目录独立保存。升级只增加选定应用的新版本产物并重建其容器，保留配置及运行数据；数据库是否允许回退需另行判断，不承诺自动回滚迁移。

打包执行必要构建并生成交付文件，不执行迁移、启停容器或远程部署。server 使用 Java21 Maven 校验与构建，web 使用 Node24 锁文件安装、类型检查和生产构建；infra 不要求这些编译工具。只收集白名单中的产物和模板，不把 `.env.dev`、真实密钥、证书私钥及运行数据纳入压缩包。版本字符串受限，已有输出拒绝覆盖，失败不发布不完整成品；Web构建目录中的符号链接和私密配置文件拒绝归集。

运行时镜像固定为 Temurin21.0.13_9-jre-jammy、Nginx1.30.6-alpine、MySQL8.0.45、Redis7.4.11、Flyway12.4.0，支持配置经过核对的镜像地址或digest。Flyway官方12.4.0镜像仅提供linux/amd64，模板明确该平台；其他架构需准备可用的同版本镜像或验证仿真，不把当前macOS检查当作目标容器运行证据。

## 网络与入口

沿用现有架构：同机组件通过明确命名的外部 Docker 网络通信；跨主机连接使用配置的内网地址。本次生产配置显式接入共同外部网络，原开发配置保留。

已有 Nginx 直接运行于宿主机并承接 HTTPS。请求路径为：宿主机入口 Nginx → 宿主机回环地址的 web 映射端口 → web 容器 Nginx → server；web 容器 Nginx 同时提供静态内容与 `/api` 转发，server 通过内部网络访问 MySQL/Redis。

仅将 web HTTP 端口映射到宿主机回环地址，默认为 `127.0.0.1:18081:80`，宿主机 Nginx 代理到 `http://127.0.0.1:18081`；端口可配置，部署时检查占用。web 到 server、server 到同机 MySQL/Redis 使用共同的外部 Docker 网络，默认名lookmate，各项目通过明确的服务别名通信。server、MySQL、Redis 的生产默认配置不发布宿主机端口；开发配置中用于 IDE 连接的回环端口不沿用为生产默认值。

交付包附已有 Nginx 的站点接入示例，由用户合并到现有配置，保留现有证书及 TLS 配置，不新增入口 Nginx 实例。入口覆盖客户端传入的转发头，web 保留HTTPS、Host、端口与客户端地址并清除Forwarded；server启用Tomcat原生代理头处理，Cookie保持Secure。Web代理按Docker DNS重新解析后端地址，API错误不回退单页页面，写请求不自动重试。

部署说明顺序为：创建外部网络 → 分别启动 MySQL/Redis 并确认就绪 → 显式执行配套迁移 → 启动 server → 启动 web → 合并入口代理配置并检查。package.sh 不执行部署；跨 Compose 的就绪条件由操作者检查。

## 实施边界

1. 本次提供MySQL/Redis同机默认方案，实际域名、凭据、绝对运行路径和端口由目标机器配置。
2. 不自动改动宿主机Nginx、证书或reload，不新增HTTPS入口。
3. 不实现deploy.sh、自动维护排空或数据库回滚；停止宽限不能替代发布前停止接收工作与等待任务结束。
4. 验证使用本地构建、隔离检查和占位配置，Docker容器运行、真实HTTPS登录、数据重启保留及外部服务联调另行记录。

## 验收条件

- server/web 可分别打包；infra 可单独归集 MySQL/Redis 配置，all 包含应用、中间件配置及配套迁移文件和驱动。交付包携带版本及校验信息。
- 构建失败时退出并报告失败，不将不完整结果作为成功交付包。
- 解压后可明确找到各组件独立 Compose、程序文件、配置模板和说明，部署无需业务源码与本机编译工具。
- Compose 配置可解析；实际启动验证待目标环境进行，本次打包不执行真实供应商调用、共享库迁移或公网部署。
- 压缩包不包含本地真实配置、密钥、证书私钥或持久化数据；升级保留实际配置与运行目录。
