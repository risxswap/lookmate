# 穿搭算法设计

创建日期：2026-10-21。

状态：2026-10-21 用户确认核心算法方案：程序筛选候选、一次模型规划、程序校验后生图，以及按近期组合辅助取舍。业务原则见 [需求说明](01-需求说明.md) 和 [领域模型](../../01-项目总览/02-领域模型.md#衣橱自动搭配已确认)。候选目标 24、类别名额、约三分之一探索名额与历史窗口 10 作为可调整的联调初值，非已验证生产配置。内部数据结构仍需完成契约与持久化映射；本文列出的业务与技术待决项不因整体方案确认而自动确定。尚未实施、未调用真实模型，本文件不是实施计划。

## 目标与已有基础

一次提交生成一套可解释的穿搭和一张效果图。沿用现有衣橱、必穿、可选尺寸、适度尝新、允许无鞋及一次提交自动完成的规则。首版采用程序筛选、一次模型规划、程序校验、生图的固定流程，不引入向量数据库、训练推荐模型或多代理循环。

现有代码 DressFeatures 与 WardrobeService 已提供图片视角、描述、颜色数组、图案、风格标签、版型、材质外观及领口等细节，有效特征按人工字段覆盖当前有效 AI 字段，显式 null 不回退。图片特征不等于整件单品的确定属性；不把细节图颜色当作衣服主色，不把材质外观当作真实成分。现有数据不足以精确判断服装是否合身、保暖温度或透气性能。

已有设计输入 JSON、任务图片引用、固定方案栏目和单品明细可承载主要流程。当前没有设计执行模块，新增内部字段的持久化映射仍须实施前核对，不因已有 JSON 字段就视为兼容性验证完成。

## 1. 固定当次上下文

输入分为本人照片、实际使用的个人属性与可选尺寸、长期偏好、当次要求、必穿 ID、单次限制例外、衣橱候选、近期组合摘要。年龄沿用提交日期计算，未提供的内容保留未知，尺寸附 cm/kg 单位。

2026-10-21 已确认：场合、风格和普通偏好默认作为尽量满足的目标；必穿、明确禁忌及语义明确的“必须、不能、只接受”等要求作为硬要求。含义不清不擅自升级，在结果中说明理解与取舍，但不能降低既有明确限制。否定、引用和条件表达须结合完整语义判断，不按关键词直接生成硬约束。硬要求冲突或无法满足时说明原因并停止。

明确要求与一般偏好分开。结构化字段能确定的冲突在提交前处理；自由文字完整保留给规划模型，首版不靠关键词保证理解全部复杂冲突，也不增加一次前置模型调用来解析场合。模糊语义不能在程序筛选阶段硬排除衣物。

候选选择参数、排序种子、历史摘要、提示词版本和图片预算均进入当次快照。新提交使用新种子；幂等重复提交返回原任务，不重新挑选；沿用原快照重试不读取后来变化的衣橱或历史。仅重试生图完全复用原方案。

## 2. 程序筛选候选

### 可用性与硬边界

基础条件是当前账号的有效单品、有效分类、名称及至少一张可用图片。识别失败或未完成不作为排除理由。必穿项强制进入候选；不可用或预算容纳不了时明确拒绝，不静默忽略。

程序仅对可可靠判断的结构化硬限制排除单品。一般不喜欢的颜色、风格不匹配、季节为空、缺少尺寸、最近穿过都不作为硬排除条件。明确文字限制交给模型检查，程序不宣称已验证全部语义限制。

### 类别覆盖与多样性

建议候选目标为 24 件，可配置，仅作为联调初值，不代表供应商支持此图片数量。小衣橱在预算内全部纳入。大衣橱先纳入必穿项，再分组填充；不直接取全局分数最高的 24 件。

初始类别额度建议：上装 6、下装 5、连衣裙 3、外套 3、鞋 3、包 2、配饰 2。必穿项计入对应额度；某组必穿超过额度时保留全部必穿，减少其他组剩余额度；若必须减少到无法保留基本组合路径，明确报告容量限制。某组不足时，优先给上装、下装、连衣裙等基础组合路径补位，再分给其他组，不强制凑满。类别只是候选覆盖，不能把每套搭配限定为每类一件，也不能仅凭外套分类断定不能单穿。

每组非必穿名额建议约三分之二按已知偏好与当次结构化要求匹配选取，其余保留给不同颜色、风格及信息不足的单品。程序只做版本化词表归一和可解释匹配；未识别词不等于不匹配，不通过自由文字猜测禁忌。无匹配依据时，用颜色/风格分组轮换与稳定种子打散，避免一直选最新录入的衣服；ID 作为最终稳定排序键。近期单品使用频率只作同等候选的弱排序依据，不剔除频繁使用的基础款或必穿项。

候选缩减意味着可能遗漏更佳组合。记录可用单品数、入选数、各类别覆盖、未入选原因及是否截断；规划不成功时不能把“候选中没找到”说成“整个衣橱不存在”。

### 数据读取与事务

候选在提交事务中固定，遵守先锁 user 的既定规则。在有界数据规模内只读取排序必要的轻量属性，批量加载最终候选的图片与特征，校验并写快照及引用；所有外部模型、签名获取后的图片处理均在事务外。

衣橱扫描上限、字段大小及事务耗时必须通过真实规模验证。超出安全扫描容量时明确报告限制，不只取最新 N 件再声称检查了全衣橱。首版不以无限读取整库解决候选问题，也不在事务外选完后未经版本/归属复核直接写快照。提交算法的锁顺序与容量阈值随实现细化。

## 3. 图片预算

规划预算与生图预算分开，均限制图片张数、总字节数、尺寸及文本长度。未配置且未验证渠道预算时不开放真实生成，不使用文档中的供应商历史上限作为部署默认值。

建议规划为每件候选选择一张代表图：优先有效视角为 FRONT 的图片，否则使用封面；有余量时再给必穿项补充背面或关键细节图。若封面仅为细节图且其他图也无法看清整件，保留不确定性，由模型决定是否足以搭配，不编造轮廓。

候选图片快照与实际送模图片清单分别记录。沿用既有候选图片引用保留规则，不因某图本次没送模就丢失任务引用。预算不足时先减少补充图，再按候选优先级缩减非必穿项，保证每件实际候选至少有一张送模图，并记录最终覆盖情况。

生图优先每件选中单品一张代表图，余量再加细节图，同时保留一张本人照片。规划输入提前给出可选单品数量预算；选中结果超预算时校验失败，不能悄悄删掉某件衣服。图片地址由服务端在调用时生成，模型只返回图片 ID，不接受模型自造 URL。

## 4. 一次规划调用

请求按固定区块组织：系统边界、当次硬要求及例外、当次一般目标、本人资料与照片、长期偏好、候选列表与编号图片、近期组合摘要、输出结构。用户备注和图片文字作为资料，不得覆盖系统边界。衣物名称和分类最终由服务端快照回填，避免模型改名或混淆来源。

模型先判断候选能否满足硬约束和基本穿着需求，再比较数个可行组合，最终仅返回一套。返回可核查的结论和简短理由，不要求输出内部逐步思考或虚假的精确审美分数。

组合取舍顺序建议：先满足必穿与明确限制，再满足当次场合和明确设计目标，再综合比较配色、比例、层次、可判断的舒适性及长期偏好；在质量相近时优先不重复的组合。默认协调、适度尝新。质量优先于新颖度，不把所有判断强制加权为一个分数。

未选用衣橱鞋子不影响可行性；效果图允许补充示意鞋，须提示其非衣橱来源，不替代必穿鞋子。一般场合目标无法充分满足时允许近似方案并说明差距。硬要求相互矛盾或基本穿着不成立时不生图。2026-10-21 已确认基础组合为上装＋下装，或可独立穿着的连衣裙、连体服装；外套是否需内搭按款式判断，不能仅靠单品类别判定覆盖充分。不支持局部搭配，本人照片中的衣物不自动视为候选。缺少基础衣物时提示补充，不补造或沿用未入库衣物。

## 5. 规划输出草案

2026-10-21 已确认天气与季节按整套搭配判断，见 [领域规则](../../01-项目总览/02-领域模型.md#衣橱自动搭配已确认)。候选筛选不得仅因季节标签与当次环境不同就硬排除单品；规划结合用户提供的环境考虑层次、覆盖程度与穿脱方式，说明能力未知或目标未充分满足的局限。室内外穿法属于同一方案，主效果图遵守必穿与明确展示要求，不增加第二套方案或效果图。

2026-10-21 已确认必穿须实际穿用并允许正常遮挡，详细定义见 [领域规则](../../01-项目总览/02-领域模型.md#衣橱自动搭配已确认)。规划不能仅因同类必穿项数量超过一件就判冲突，应结合款式判断叠穿或组合是否成立，并在穿法中说明。明确要求展示的细节须纳入硬要求判断及生图方向；程序检查必穿 ID 覆盖不等于验证实际穿用或细节可见，后者继续通过图文样本验收。

信息不足的判断尺度已于 2026-10-21 确认，见 [领域规则](../../01-项目总览/02-领域模型.md#衣橱自动搭配已确认)。规划时区分普通审美判断与影响硬要求、基础穿着的未知项：前者允许合理取舍并说明不确定性，后者须寻找有依据的其他组合，找不到才停止。寻找组合在同一次规划中完成，不增加模型调用，也不放宽必穿要求。候选被截断时，仍只描述本次候选的判断范围。

2026-10-21 已在 [生成技术契约草案](03-生成技术契约.md) 细化为 kind/plan/noMatch 分支及公共结果字段。下列为原算法讨论结构，正式实施应在契约确认后统一采用一个 schema，不同时支持两套命名；失败映射与字段保存建议见该文。

内部结构建议如下，不是新增公共 API 契约。ID 使用字符串，字段长度与数量限制在实现前按现有数据库及通用协议对齐。

```text
schemaVersion
decision: READY | NO_MATCH
matchLevel: EXACT | APPROXIMATE       # READY 时必填，表示目标匹配，不是图片保真度
title / summary / style / occasion / designReason
colorAdvice / wearingAdvice
items[]: dressId, referenceImageIds[], matchReason, wearingMethod, role
constraintChecks[]: constraintId, SATISFIED | CONFLICT | UNCERTAIN, explanation
limitations[]: code, description
novelty: changed, closestRecentTaskId?, explanation
imageDirection: wearingDetails, composition
illustrativeShoes?: description       # 非衣橱示意鞋，无 dressId；字段映射待细化
noMatchReason                          # NO_MATCH 时必填
```

READY 必须包含完整固定方案栏目及单品明细。APPROXIMATE 必须说明未满足的一般目标；使用示意鞋、仅用局部照片等限制单独说明。NO_MATCH 不生成图片，不伪造可用方案。EXACT 仅表示模型判断当次目标满足，不证明真实合身或最终图片无偏差。

程序从 items 推导 selectedDressIds，避免维护两份容易不一致的单品列表。role 是方案中的穿着角色，不修改衣橱分类。未决硬约束不能返回 READY；模型对自由文字的校验结论仍不是确定性验证保证。

固定展示字段可映射到 design_result 与 design_result_item；limitations、constraintChecks、novelty 等需要评估 plan_provenance 的版本化保存和对外返回方式，不能假定当前 DTO 已支持。2026-10-21 已确认面向用户清晰展示差距、理解与取舍；影响使用的限制和示意鞋提示放在效果图附近，不能仅保存在内部 JSON 或埋在长说明中。现有固定栏目继续承载真实单品、穿法及对应当次要求的配色、比例、场合理由，不展示缺乏依据的搭配评分。NO_MATCH 对应公开状态及业务错误码、三模式兼容与迁移仍需契约设计；当前不新增任务状态或修改 SQL。

## 6. 程序校验与生图

程序校验 JSON 结构、字段类型/长度、未知字段、单品与图片 ID、重复单品、必穿覆盖、图片归属及预算、设计模式适用栏目和可机器判断的硬限制。模型不得引用候选外单品，引用图片必须属于所选单品的当次快照。

程序能证明编号和资源约束正确，不能单靠这些校验证明搭配好看、符合全部文字限制或图片保真。语义和图文质量通过联调样本验收，首版不自动增加第二次审核模型调用。

有效文字方案及明细原子保存后进入生图。服务端组合固定人物/服装保留规则、已验证的单品与图片映射、模型穿法及构图方向，形成最终 image_prompt；不直接把一段不受约束的模型自由提示词原样交给生图端。照片不主动瘦身或拉长腿，单项穿搭保留发型；除未选用衣橱鞋子时允许补充示意鞋外，禁止衣橱外服饰。示意鞋单独记录生成意图，无衣橱 ID 或实物参考图；服务端根据该标记确保结果出现非衣橱提示，不只依赖模型自觉写进说明。具体持久化与接口字段待细化。仅发送本人照片和选中单品参考图，不把整批候选图交给生图模型。

格式错误、非法 ID、漏必穿或超预算时停止，不自动修复、重选或增加模型调用。NO_MATCH 与技术失败分别保留原因，但公开状态映射待确认。生图失败保留文字，结果未知沿用既有 UNKNOWN 及手动重试规则。2026-10-21 已确认无衣橱鞋子时可生成示意鞋并提示，不要求裁切脚部；原照片鞋子不能冒充已选衣橱单品。已选衣橱鞋子时不允许用示意鞋替换。

## 7. 近期组合变化

建议读取本人最近 10 个未删除、未隐藏且完整成功的含穿搭任务（含整体设计），仅传递任务 ID、所选单品 ID、基础穿搭角色、场合及风格摘要，不传历史照片。10 为可配置初值；同一套方案仅重试生图形成的重复成功记录按来源去重。历史窗口与摘要随新任务固定。

候选数量有界时可对最近记录计算组合相似性：全部单品 ID 排序集合相等视为完全重复；基础衣服相同而仅替换包、饰品或鞋，仍视为主体近似。使用集合交并比作为辅助信号，不直接变成审美评分；角色缺失的旧记录只比较完整集合，不能凭空推断主体。

最近 10 条按时间读取，不在查询阶段用自由文字完全相等过滤；由模型结合场景判断参考价值，避免同义要求漏检。程序计算重复程度供解释与验证，但不因重复就拒绝合法方案。没有同样合适的其他组合时允许重复，并如实说明，不能通过改变展示顺序假装换了一套。

## 8. 验证计划

使用经授权的固定测试资料及衣橱快照，覆盖：小衣橱全部纳入、大衣橱类别覆盖、未识别单品、人工 null 覆盖、必穿跨类别、基础衣物缺失且照片含未入库下装、连体服装独立穿着、外套需内搭、图片超预算、无鞋时示意鞋提示、已有鞋子不被示意鞋替换、示意鞋不伪造单品 ID、自由文字冲突、否定表达不误判为硬要求、一般目标近似满足与硬要求失败的区分、只有一套适合、同义要求再次生成、仅换配饰、候选不足但衣橱未全部入选、提交后换图或删衣、仅重试生图。

确定性检查关注候选/图片归属、必穿覆盖、预算、快照稳定性、无自动重发。语义验收人工核对场合与限制、整套协调性、差距说明是否诚实、人物和服装保留及图文一致；保留模型和提示词版本，不以一次好结果代表稳定可用。

联调比较不同候选容量的遗漏情况、耗时与成本，再确定配置。规划失败率、超预算率、必穿遗漏率、重复组合率分别记录；不把重复率越低视为越好。本轮仅核对现有文档和数据结构，未执行上述测试。

### 原优化建议（仅保留调研依据）

1. **让候选更容易组成完整搭配。** 当前分组额度与单件偏好排序能保证类别数量，却不能保证入选单品彼此适配。建议在已有类别覆盖与探索名额内，加入围绕必穿项的互补候选，以及有依据的不同基础组合路径；无必穿时保留多个方向。只使用已有可靠属性进行软排序，不新增前置模型调用，不把同色或同风格直接等同于兼容。不能确定时保留多样性。确切排序规则及名额分配待样本比较，不在本轮编造权重。
2. **图片缩减后重新检查组合覆盖。** 原文要求保证最终图片覆盖，但预算缩减可能破坏先前候选的类别与搭配路径。建议每次缩减都重新核对必穿、已知基础路径及类别覆盖；优先减少重复方向或可选配饰，不能仅按单件排序机械删除。程序只检查有依据的覆盖条件，不声称能确定衣服是否适合独立穿着。
3. **把穿法变成可校验的结构。** 当前 role、wearingMethod 和 imageDirection 可承载说明，但缺少统一的层次关系。建议细化内外层、敞开/扣合、塞衣角、必须可见的细节及其对应单品；检验引用是否合法、层次关系是否自相矛盾，再据此组合生图提示。结构校验不证明图片实际遵守。字段、值域及持久化映射仍待契约设计，不新增第二次规划或审核调用。
4. **优先完整且清晰的参考图。** 当前 FRONT 优先、否则封面的选择可能选到被遮挡或裁切的图片。建议在已有可靠图像信息足够时，先判断整件可见与主体清晰，再比较视角；关键细节图在预算内补充。没有质量依据时保留未知，不增加强制抠图或前置识别调用。人物照片的姿态、覆盖范围与清晰度准入仍是待决项，应在真实联调前明确。
5. **区分推荐历史与偏好证据。** 完整生成成功说明系统推荐过，不说明用户喜欢或实际穿过。近期组合继续只用于变化参考。若以后利用收藏学习偏好，也不能把整套收藏解释为喜欢其中每件单品；新增反馈及学习机制另行讨论，首版不自动加入。
6. **分开评测候选、规划与生图。** 现有验证计划已有规则与质量检查，建议补充阶段归因：候选是否遗漏人工认可组合所需单品、规划是否遵守硬要求并形成合理搭配、效果图是否保留人物与单品并执行穿法。用固定授权样本比较原筛选与互补筛选，记录预算、延迟与成本；在预算允许的小衣橱上用全部候选作对照。主观协调性使用盲评，重要分歧复核。测试集与提示词调整样本分开，组合可有多个合理答案，不把某一套当唯一正确解。上线阈值待样本结果确定。

### 原建议推进顺序（已由第 10 节替代）

先细化候选互补、预算缩减后的覆盖检查、穿法结构及离线评测，再以真实样本确认当前规划和生图组合能否满足要求。FashionCLIP、专门训练的推荐模型及专用试穿渠道保留为后续备选；只有候选遗漏、规划质量或图片保真问题有证据时，再评估引入成本。现有一次规划、无自动修复调用和无自动重生规则保持有效。

## 10. 首版简化方案（2026-10-21 已确认，待实现）

保留程序筛选候选、一次模型规划、程序校验后生图的现有流程，不增加模型、调用次数或复杂推荐算法。具体取舍如下：

- 候选筛选保持必穿优先，其余按类别、已有偏好与多样性补齐。暂不做互补打分或额外的组合检索算法，最终搭配由现有规划模型决定。图片预算缩减后，程序再次检查必穿项及基础类别覆盖，避免误删关键候选；类别检查不代替模型对完整穿着的判断，也不新增每类只能一件的限制。
- 穿法继续使用现有文字字段，由规划模型说明内外层、敞开或扣合、需要露出的细节，作为服务端组合生图提示的输入。不新增复杂的穿搭关系结构，不额外调用模型整理穿法；仍沿用固定人物和单品保留规则及已有 ID、归属、预算校验。
- 使用少量固定且经授权的案例验证，重点检查必穿遗漏、基础搭配完整性、是否补造衣物，以及效果图与文字是否一致。不建设独立评测系统；已有确定性校验和关键失败场景仍保留，未测试项如实记录。
- FashionCLIP、自训练推荐模型和专用试穿服务不纳入当前方案。先完成一次规划选衣与一次生图的链路，再依据实际问题局部调整，不提前引入复杂优化。

本节替代第 9 节中增加互补筛选、复杂穿法结构和评测建设的建议。既有业务规则、手动重试、结果未知不自动重发以及无自动审核和重生约定保持有效。本轮仅确认设计与范围，未授权编码、迁移或付费模型调用，尚未实施或执行验证。
