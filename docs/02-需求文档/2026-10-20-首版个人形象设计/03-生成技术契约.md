# 生成技术契约

创建日期：2026-10-21。

状态：已按本契约完成代码及开发验证，真实供应商联调待完成。用户已授权完整生成链路，预览签名、NO_MATCH 映射 FAILED、32 KiB 请求上限及 V3 outcome_snapshot 迁移已纳入本轮实现，见 [实施计划](04-生成实施计划.md)。业务原则见 [需求说明](01-需求说明.md) 和 [算法设计](02-穿搭算法设计.md)，公共格式沿用 [接口契约](../../01-项目总览/05-接口契约.md)。真实渠道与模型效果尚未验证。

## 实施前基线与兼容范围

实施前 DesignController 只实现 GET 列表和详情。列表使用 TaskSummaryDto，详情扩展 result；已有结果包含固定文字栏目、hairstyle 和 items，尚无输出图片、提示列表和输入摘要。实施前 RecordsService 只接受 HAIRSTYLE / OUTFIT。工作台和列表已使用 QUEUED、PLANNING、GENERATING、SAVING、SUCCEEDED、FAILED、UNKNOWN。

本方案新增提交预览、提交、按提交键找回及重试，扩展详情和模式，保留既有字段名称及响应包装。删除、隐藏和收藏继续沿用已有规则；未实现的操作不能仅因写入本文就出现在 actions 中。

整体设计编码采用 OVERALL；保留 HAIRSTYLE、OUTFIT。不新增任务状态：无法搭配使用 FAILED 和专用业务错误码，详情 GET 仍返回 200。模型内部 READY / NO_MATCH 不成为公开任务状态。

## 公共字段规则

- 登录账号来自会话；所有 POST 使用现有 CSRF。资源不属于当前账号时返回 404，不泄露资源存在性。
- ID 为正十进制字符串，符合当前 Long 范围；version 为非负十进制字符串，不转 JavaScript number。时间为 UTC ISO 8601，年龄计算仍用 Asia/Shanghai 日期。
- 未定义请求字段、重复 JSON 键、重复 ID、错误类型和超长内容均拒绝，不静默丢弃或截断。对象内嵌字段同样检查。
- 本文字符串长度按 Unicode 码点计算。普通可选文字允许省略、null、空串，归一为空；非空文字去首尾空白、CRLF 归一 LF，保留内部内容，不改写用户含义。
- 成功包装为 data/requestId，失败为 code/message/requestId，可附 fieldErrors；本文示例未列出的已有详情字段仍保留。不返回模型原始响应、密钥、供应商 URL 或生图提示词。
- 请求 JSON 上限为 32 KiB；图片通过现有文件 API 上传，请求中不接收 Base64 或远端 URL。该大小是应用限制，不代表渠道限制。

## 1. 用户输入结构 DesignInput

预览和提交共用同一输入结构。提交前页面展示真正会使用的照片、资料、尺寸和必穿单品；默认照片只用于页面预选，提交必须传具体 personFileId，不在后台悄悄换图。

| 字段 | 类型及默认 | 校验与语义 |
| --- | --- | --- |
| designType | 必填字符串 | HAIRSTYLE / OUTFIT / OVERALL |
| personFileId | 必填 ID | 本人已核验可用文件，恰好一张；可为临时上传 |
| profileVersion | 必填 version | 页面读取的资料版本；保护本次资料及限制确认，不是用户手填项 |
| requirements | 可选文字，默认空 | 最多 2000；本次完整要求，不接受客户端提供解析后的硬约束来替代原文 |
| occasion | 可选文字，默认空 | 最多 100；普通场合目标，未填按日常穿搭，不声称存在明确着装规范 |
| style | 可选文字，默认空 | 最多 100；本次一般风格目标 |
| weatherNote | 可选文字，默认空 | 最多 200；用户提供的天气/温度文字，不自动查询天气 |
| requiredDressIds | 可选数组，默认 [] | 无重复的本人单品 ID；null 拒绝；仅涉及穿搭时允许非空 |
| useMeasurements | 可选布尔 | OUTFIT / OVERALL 默认 true；HAIRSTYLE 默认 false，仅允许 false |
| measurementId | 可选 ID 或 null | useMeasurements=true 时省略/null 使用当前尺寸；明确 ID 使用本人历史尺寸；false 时必须省略/null |
| constraintOverrides | 可选字符串数组，默认 [] | 本次明确允许突破的长期限制标识，去重校验；null 拒绝，含义见预览流程 |

HAIRSTYLE 不接受非空 weatherNote、requiredDressIds 或尺寸输入；其 occasion/style/requirements 仍可填写。模式与输入不适用时返回字段错误，不静默忽略。

requiredDressIds 的硬容量来自已启用的规划/生图预算；预览返回 maxRequiredDressCount，不以候选目标 24 充当必穿上限。部署预算未验证、生成未启用时返回 503 GENERATION_UNAVAILABLE，不凭空设置渠道上限。

useMeasurements=true 但没有当前有效尺寸仍允许生成，预览展示 measurementState=NONE；指定的历史尺寸不存在则 404，不静默切换。关闭尺寸时模型输入不含尺寸。系统读取性别、年龄、偏好，不接收客户端自造的个人画像；缺失值保留未知。

## 2. 提交预览 POST /api/designs/preview

请求体直接为 DesignInput。不创建任务、不占设计名额、不预留队列容量、不调用模型，也不向供应商传图片。建议按账号限制预览频率，具体阈值随实现配置。

返回 200：

```json
{
  "data": {
    "canSubmit": true,
    "previewToken": "opaque-signed-token",
    "expiresAt": "2026-10-21T08:10:00.000Z",
    "inputDigest": "sha256-of-normalized-input",
    "personalContext": {
      "profileVersion": "12",
      "gender": "FEMALE",
      "age": 30,
      "ageAsOf": "2026-10-21",
      "measurementState": "NONE",
      "measurementId": null
    },
    "restrictions": [
      {"id": "NO_HIGH_HEELS", "text": "不穿高跟鞋", "overridden": false}
    ],
    "conflicts": [],
    "notices": [
      {"code": "NO_MEASUREMENTS", "severity": "INFO", "message": "本次没有有效尺寸，将依据照片和其他资料规划"}
    ],
    "limits": {"maxRequiredDressCount": 8},
    "semanticCheck": "NOT_EXHAUSTIVE"
  },
  "requestId": "request-id"
}
```

示例中的 8 仅展示返回类型，实际值取已验证配置。完整 personalContext 还返回实际生效的 preferences、使用的尺寸对象及 measurementUnits（cm/kg）；不返回原始生日。personFileId 和必穿单品返回可展示的文件/名称摘要，签名 URL 通过文件访问接口获取。profileVersion 与请求不同则 409 PROFILE_CHANGED，保留用户输入并刷新比较。预览扩展字段统一为 personPhoto={fileId}、requiredDresses=[{dressId,dressName,categoryName,imageFileIds}]；数组保持界面展示顺序，但摘要按 ID 集合计算。personalContext.preferences 复用资料 API 的 13 字段结构，不使用未保存的前端偏好草稿；measurements 为既有 27 项值的对象或 null，measurementUnits={length:"cm",weight:"kg"}。

限制标识：已有结构化 restrictions 使用稳定编码；染发/烫发拒绝分别使用 DYE_REJECT/PERM_REJECT，仅在涉及发型时生效；restrictionNote 使用 `restrictionNote:<原文SHA-256>` 标识整个当前文本。界面展示完整原限制，不能让例外默默扩大为豁免全部限制。首版对自由文本不做自动拆句豁免；如果用户只想放宽其中一部分，应修改当次说明并在后续设计中再细化粒度，不把整段例外伪装成局部豁免。

流程为预览 → 展示原限制与可确定冲突 → 用户选择仅本次允许或修改要求 → 输入有变化则重新预览 → 提交。全部当前有效限制均可查看，例外默认空，不预勾选。未知、已不存在或不适用于当前模式的例外 ID 返回 400。当前要求中的硬限制不能通过长期限制例外消除。

已知且未解决的结构化冲突返回 200、canSubmit=false、previewToken=null，conflicts 每项含 restrictionId、requirementExcerpt、message；其他必填/资源错误沿用 400/404/409。当前确定性检查覆盖：必穿单品人工标注 fit=SLIM，且长期 NO_TIGHT 未被本次例外覆盖时，按项目既有版型与限制规则返回冲突。AI标签不用于该硬拦截，不根据含糊图片标签猜测鞋跟或版型。NOT_EXHAUSTIVE 表示未穷尽语义，不显示“已确认完全无冲突”。复杂文字冲突若到规划阶段才发现，任务失败并引导修改/确认例外后新提交，不在当前任务中途等待确认，也不自动重跑。

建议 token 有效期 10 分钟，由服务端签名，绑定账号、规范化输入摘要（包括例外）、profileVersion、必穿单品预览内容摘要、Asia/Shanghai 预览日期和策略版本。token 只含定位信息/摘要，不内嵌敏感资料；签名密钥保留在受控配置，不使用 Redis 保存业务 token。不新增预览表或可执行任务。

提交事务重新校验 token 和绑定内容；跨本地日期、资料改变或必穿内容改变需重新预览。非必穿衣橱候选在正式提交时筛选固定，预览不承诺锁定全衣橱。token 过期不等于已提交任务失效。

本预览机制沿用提交前确认的业务要求，但不能保证所有自由文字冲突都在任务创建前检出。若要求提交前完成模型级语义检查，需要额外调用和状态设计，超出当前一次规划方案。

## 3. 正式提交 POST /api/designs

请求头 Idempotency-Key 建议为小写 UUID v4，由前端一次明确提交时生成；服务端限定为规范 36 字符格式。请求体：

```json
{
  "input": {
    "designType": "OUTFIT",
    "personFileId": "101",
    "profileVersion": "12",
    "requirements": "通勤，方便走路，希望正式一些",
    "occasion": "日常通勤",
    "style": null,
    "weatherNote": null,
    "requiredDressIds": ["201"],
    "useMeasurements": true,
    "measurementId": null,
    "constraintOverrides": []
  },
  "previewToken": "opaque-signed-token"
}
```

返回 202（新建与同键重放一致），data 为 taskId、status、statusUrl；status 是当前真实状态，重放时可能已终态，不强行返回 QUEUED。可附 Location=statusUrl。

事务顺序：认证及输入格式校验 → 锁 user → 查同键 → 校验预览与资料/必穿快照 → 检查账号名额和全局容量 → 固定候选、历史摘要、实际尺寸及模型配置 → 创建任务和文件引用、设置活动名额。沿用统一锁顺序和有界短事务。失败不留下半任务，外部调用在事务外。

去重摘要为 SHA-256，包含操作 CREATE 与规范化 DesignInput，不包含 token、requestId、当前资料内容或签名 URL；profileVersion、显式 measurementId 及例外仍属于客户端输入摘要。对象键稳定排序，ID 数组及例外按集合排序，默认值归一。省略/null/空串的可选文字等价；重复 ID 先拒绝，不能靠去重吞掉错误。

同键同摘要返回原任务，先于 token 过期、资料变化、维护门禁和新增容量检查；同键不同摘要返回 409 IDEMPOTENCY_CONFLICT。只有认证/格式有效的请求可查重，不通过幂等绕过身份验证。token 不入摘要使同输入刷新预览后可用原键恢复未知提交。

## 4. 按提交键找回

GET /api/designs/by-request/{clientRequestId}，返回 200，data 与提交响应相同；当前账号未找到返回 404 DESIGN_REQUEST_NOT_FOUND。资源查询包含仍存在的隐藏任务，只返回 taskId/status/statusUrl；隐藏任务详情访问按其独立规则处理，不因找回自动取消隐藏。

网络断开或响应不确定：先查原键；未找到时可用原键及完全相同输入重新提交。token 已过期则重新预览；若资料变化导致新输入不同，先确认旧提交结果，不能自动以新键创建第二个任务。原键查无任务不证明外部调用未执行。删除任务后去重记录不再存在，客户端不得复用已知旧键。

前端只保存恢复所需的提交键及原请求草稿，绑定账号并在退出时清理；不保存供应商信息。恢复时先查询，不因页面刷新自动创建新任务。

## 5. 任务详情 GET /api/designs/{id}

保留 TaskSummaryDto 的 id、resultId、favoriteId、designType、status、createdAt、updatedAt、title、summary、errorCode、errorMessage、actions。详情新增：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| inputSummary | 对象/null | 当次快照的照片、实际资料、尺寸、当次要求、必穿摘要和例外；旧任务未记录时 null，不补当前资料 |
| outputFileId | ID/null | 保存成功且授权可用的最终图片；SAVING/UNKNOWN 不暴露临时供应商地址 |
| failure | 对象/null | stage、category、code、message、suggestedAction；code/message 与原错误字段一致 |
| result | 对象/null | 保留已有文字栏目与明细，扩展字段见下文 |

inputSummary 结构为 {schemaVersion,request,personPhoto,personalContext,requiredDresses,constraintOverrides}：request 为规范化 DesignInput 的 designType/requirements/occasion/style/weatherNote/requiredDressIds/useMeasurements/measurementId；personPhoto、personalContext、requiredDresses 与预览结构一致，但为实际提交快照；constraintOverrides 为 [{id,originalText}]。不包含 previewToken 或原始生日。旧任务不能可靠还原的字段逐项 null，不以当前源记录补全。

inputSummary 是脱敏、面向用户的快照投影，不返回所有候选、配置、历史比对摘要或系统提示词。名称和图片来自任务快照；源单品删除后仍能按任务引用展示。涉及 OVERALL 时返回发型和穿搭两部分，任一必需部分规划失败不执行半套生成。

result 保留 id、title、summary、style、occasion、designReason、colorAdvice、wearingAdvice、hairstyle、items，新增 matchLevel、notices、illustrativeShoes、novelty。扩展示例：

```json
{
  "matchLevel": "APPROXIMATE",
  "notices": [
    {"code": "GOAL_PARTIALLY_MET", "severity": "WARNING", "message": "更适合日常通勤，正式程度低于你的预期", "placement": "NEAR_IMAGE"},
    {"code": "ILLUSTRATIVE_SHOES", "severity": "INFO", "message": "鞋子为 AI 生成示意，非衣橱单品", "placement": "NEAR_IMAGE"}
  ],
  "illustrativeShoes": {"description": "简洁的浅色平底鞋", "source": "AI_ILLUSTRATION"},
  "novelty": {"description": "沿用指定上衣，更换了下装组合"}
}
```

matchLevel 表示目标匹配，不是服装合身、图片保真或审美分数。旧任务缺少信息时为 null，不回填 EXACT。notices 无项返回 []；illustrativeShoes 没有则 null；novelty 未记录则 null。notice.code 建议枚举 GOAL_PARTIALLY_MET、INTERPRETATION、ILLUSTRATIVE_SHOES、REPEATED_COMBINATION、LIMITED_VISUAL_EVIDENCE；未知未来 code 前端按 message/severity 通用展示。placement 为 NEAR_IMAGE 或 DETAILS，重要局限及示意鞋强制 NEAR_IMAGE。

示意鞋提示由服务端根据验证后的标记生成，不能让模型省略；存在选中真实鞋子时 illustrativeShoes 必须 null。示意鞋不进入 items，不生成 dressId，不增加衣橱记录。IMAGE_ONLY 复制相同示意鞋说明及提示。

items 保留既有字段，增加 role 与 imageFileIds（任务快照 ID 数组）；原名称与类别服务端回填。旧记录缺少图片时返回 [] 并显示“当时未记录参考图”，不跳到当前单品图片。文件访问继续 POST /api/files/{id}/access；归属及历史引用必须覆盖任务，返回短期签名，过期只刷新签名，不重新生成设计。

hairstyle 沿用现有七个字段；HAIRSTYLE 的 items=[]、colorAdvice/wearingAdvice=null、illustrativeShoes=null；OUTFIT 的 hairstyle=null；OVERALL 两部分必填。资料不足但可规划的限制用 notices 说明，不能把未知精确尺寸填成数值。

规划文字成功即可返回 result；GENERATING/SAVING/FAILED/UNKNOWN 下有 result 不代表完整成功。只有 SUCCEEDED 且输出文件持久化成功才能收藏。页面应明确区分“方案已生成，效果图处理中”与完整完成。

## 6. 状态与动作

正常链路 QUEUED → PLANNING → GENERATING → SAVING → SUCCEEDED；阶段确定失败转 FAILED；外部结果无法确定转 UNKNOWN。结果暂存/上传未完成但仍可恢复时维持 SAVING，不因等待而假报失败或触发重新生图。UNKNOWN 释放账号名额，核实后的转移沿用既有恢复规则。

活动状态每 3 秒轮询，页面不可见暂停；终态和 UNKNOWN 停止持续轮询。前端不得把查询 HTTP 200 理解为设计成功，也不按 elapsed time 推算进度百分比。

建议新增动作名，保留 VIEW/FAVORITE/UNFAVORITE：

| 状态/条件 | 目标动作（仅实现后返回） |
| --- | --- |
| 活动任务 | VIEW |
| SUCCEEDED | VIEW、NEW_FROM_INPUT、DELETE，以及 FAVORITE 或 UNFAVORITE |
| FAILED，业务不可满足 | VIEW、NEW_FROM_INPUT、DELETE，不推荐原样 FULL 重试 |
| FAILED，可重新规划的技术失败 | VIEW、NEW_FROM_INPUT、RETRY_FULL、DELETE |
| FAILED，已保存有效文字且生图确认失败 | 上行加 RETRY_IMAGE |
| UNKNOWN | VIEW、REFRESH、HIDE、NEW_FROM_INPUT；不含 RETRY_* |

NEW_FROM_INPUT 是打开新提交表单，不直接调用生成；重新校验当前资源和资料，源资源删除时提示补充。UNKNOWN 新建前明确提示旧调用仍可能完成。动作只是当前可用提示，执行接口必须再次校验。未知 action 前端忽略；未实现动作不返回。

## 7. 重试 POST /api/designs/{id}/retry

新 Idempotency-Key，请求 `{ "mode": "FULL" }` 或 `{ "mode": "IMAGE_ONLY" }`，不接受其他输入或 previewToken。成功 202，返回 taskId、status、statusUrl、retryOfTaskId。摘要包含 RETRY、来源 ID 和 mode，与普通提交共享当前账号的键命名空间；同键相同重放先返回已创建任务，来源后来删除也不影响找回。新重试若来源不存在则 404。

FULL 使用原不可变输入及例外、候选和历史摘要，采用当前可执行模型配置；不是“换一套”。IMAGE_ONLY 只复制已验证的完整文字方案、明细、提示及图片引用，使用当前生图配置，不重新规划。新配置预算无法容纳原快照时返回 409 RETRY_INPUT_INCOMPATIBLE，不裁掉单品或静默换输入。UNKNOWN 返回 409 ACTION_NOT_ALLOWED，不接受原任务重试。

重试新任务独立持有文件引用，来源删除不破坏新任务。已失去有效快照/文件的旧任务不返回重试动作，请求到达仍需返回 409 RETRY_INPUT_UNAVAILABLE。失败原因不适合原样重试时引导 NEW_FROM_INPUT，不自动重提。

## 8. HTTP 错误与任务失败

创建前的错误不会生成 FAILED 任务；已经接受的后台失败通过任务详情表达，不能返回成查询接口 HTTP 500。

| HTTP | code | 前端处理 |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | 展示 fieldErrors，保留表单 |
| 401 / 403 | 沿用现有认证/CSRF 错误码 | 登录或刷新会话凭证，不自动换键提交 |
| 404 | DESIGN_NOT_FOUND / DESIGN_REQUEST_NOT_FOUND / RESOURCE_NOT_FOUND | 区分记录、键查询与输入资源缺失；跨账号与不存在一致 |
| 409 | PROFILE_CHANGED / PREVIEW_STALE / PREVIEW_EXPIRED | 保留输入，重新预览并由用户确认 |
| 409 | PREVIEW_INVALID | token 无效，重新预览；不泄露签名诊断 |
| 409 | IDEMPOTENCY_CONFLICT | 停止自动重发，核对原提交 |
| 409 | ACTIVE_TASK_EXISTS | 查询工作台展示本人活动任务，不自动创建新任务 |
| 409 | FILE_NOT_USABLE / REQUIRED_DRESS_UNAVAILABLE | 提示更换或等待核验，再重新预览 |
| 409 | ACTION_NOT_ALLOWED / RETRY_INPUT_UNAVAILABLE / RETRY_INPUT_INCOMPATIBLE | 刷新详情，按当前 actions 处理 |
| 422 | INPUT_BUDGET_EXCEEDED / WARDROBE_EMPTY | 提示减少必穿或补充衣橱，不隐藏删除必穿项 |
| 413 / 429 | REQUEST_TOO_LARGE / RATE_LIMITED | 缩小请求或按 Retry-After 等待 |
| 503 | GENERATION_UNAVAILABLE / TASK_CAPACITY_EXCEEDED / INPUT_SCAN_CAPACITY_EXCEEDED | 保留输入，允许稍后重试；不是“衣橱无合适单品” |

建议 failure.stage 取 PLAN / IMAGE / SAVE，category 取 INPUT / TECHNICAL / UNKNOWN；suggestedAction 取 EDIT_INPUT / RETRY_FULL / RETRY_IMAGE / REFRESH / WAIT，且必须与 actions 相容。以下为后台错误码提案：

| code | 状态/类别 | 表达 |
| --- | --- | --- |
| OUTFIT_NOT_FEASIBLE | FAILED / INPUT | 基础衣物不足或无法构成穿搭；若候选截断，只说本次候选未找到，不断言全衣橱不存在 |
| HARD_REQUIREMENT_UNMET | FAILED / INPUT | 明确要求无法满足；说明具体要求 |
| REQUIREMENT_CONFLICT | FAILED / INPUT | 要求互相冲突，或仍未豁免的长期限制冲突；引导修改/重新预览 |
| PERSON_PHOTO_INSUFFICIENT | FAILED / INPUT | 照片信息不足以继续，提示换图，不猜测细节 |
| PLAN_OUTPUT_INVALID | FAILED / TECHNICAL | 输出结构、编号、必穿、预算或模式校验失败；不自动追加修复调用 |
| PLAN_PROVIDER_FAILED / IMAGE_PROVIDER_FAILED | FAILED / TECHNICAL | 确定未成功的渠道错误，不显示原始供应商响应 |
| EXTERNAL_RESULT_UNKNOWN | UNKNOWN / UNKNOWN | 外部调用结果待核实，不能自动重发 |
| RESULT_SAVE_FAILED | FAILED / TECHNICAL | 仅在明确无法恢复保存且已有诊断依据时使用；保有可恢复结果时继续 SAVING，不开放重新生图 |

NO_MATCH 内部原因映射到上述四个 INPUT 错误，model_call 可记调用 SUCCEEDED、design_task 记 FAILED，两者不矛盾。仅生成文字不算完整成功，不收藏失败或未知任务。

## 9. 规划模型内部契约 V1

这是服务端适配器的数据结构，不是前端 API。候选、个人资料、有效限制及引用 ID 都由服务端构造；每条输入限制分配 constraintId，模型新增从当次文字识别的限制须带 source=REQUEST_TEXT 与原文摘录，不能伪造用户已经同意例外。

输入包含 schemaVersion、designType、personalContext、normalizedRequest、effectiveConstraints、candidateItems、personImage、imageBindings、recentOutfits、budgets。candidateItems 保留 dressId、图片 ID/有效特征及来源，imageBindings 绑定本次真实送模的图片；当前生日、密码、签名密钥及其他用户数据不进入请求。

输出采用有明确分支的结构，所有对象拒绝未知字段：

```text
schemaVersion = 1
kind = READY | NO_MATCH
plan = READY 时对象 / NO_MATCH 时 null
  title, summary, style, occasion, designReason
  matchLevel = EXACT | APPROXIMATE
  colorAdvice, wearingAdvice
  hairstyle = 七个既有字段 / null（按模式）
  items[] = dressId, referenceImageIds[], role, matchReason, wearingMethod
  limitations[] = code, message, severity
  interpretations[] = requestExcerpt, interpretation
  illustrativeShoes = {description} / null
  novelty = {closestRecentTaskId?, explanation} / null
  imageDirection = {wearingDetails, composition}
constraintChecks[] = constraintId, result(SATISFIED/CONFLICT/UNCERTAIN), explanation
requestConstraints[] = id, source(REQUEST_TEXT), excerpt, strength(HARD/SOFT)
noMatch = NO_MATCH 时对象 / READY 时 null
  reasonCode = INCOMPLETE_OUTFIT | HARD_REQUIREMENT_UNMET | REQUIREMENT_CONFLICT | PHOTO_INSUFFICIENT
  message
  relatedConstraintIds[]
```

READY 的所有生效硬限制必须为 SATISFIED；不能输出冲突/未知却继续生图，也不能用例外豁免系统边界。NO_MATCH 不能携带可执行 plan。程序检查服务端限制完整覆盖、ID 合法、请求摘录确实来自原文；语义强度仍需模型理解，程序不能保证完整召回自由文字要求。

输出限制建议：title 100、style/occasion 各 255、summary/designReason/colorAdvice/wearingAdvice 各 4000；单品理由及穿法各 2000；示意鞋描述 500；每条提示 500、最多 20 条；interpretations 每段 500、最多 10 条；imageDirection 两项各 2000；constraintChecks/requestConstraints 最多各 64、解释 500；noMatch.message 1000；role 为 TOP/BOTTOM/ONE_PIECE/OUTERWEAR/SHOES/BAG/ACCESSORY；hairstyleName 最多 100，其余六个 hairstyle 说明字段各最多 2000，均非空。items 数量受已验证生图预算约束，不能用 64 等输出上限覆盖渠道预算。内部总响应建议最多 128 KiB，超限作为无效输出，不截断 JSON。

referenceImageIds 必须来自所选单品的任务候选快照，并满足实际可提供的参考预算；模型不能指定自己没见过的图片作为设计依据。必要的额外生图参考由服务端按已固定快照选择并记录，不让模型编造图片链接。dressName/categoryName 服务端从快照回填。真实鞋子与 illustrativeShoes 互斥；示意鞋无引用 ID、不算完整衣物覆盖、不进入近期组合的实物 ID 集合。

原算法文档中的 decision/noMatchReason 等探索字段以本文 kind/noMatch 分支为准；实现只维护这一套 schema。模型原始 JSON 不是可执行指令，文字按纯文本显示。无效输出不自动修复或追加模型调用。

## 10. 持久化与迁移

| 数据 | 保存位置 | 约束 |
| --- | --- | --- |
| 不可变输入、资料、例外、候选、历史与规范化摘要版本 | design_task.input_snapshot（schemaVersion=2） | 不写回当前偏好，不在任务运行中修改输入 |
| 模型配置、提示词版本及预算 | model_config_snapshot | 不含密钥，保留旧配置执行能力 |
| 固定文字与真实单品 | design_result、design_result_item、design_result_hairstyle | 按模式同事务保存；OVERALL 同时拥有两类明细 |
| 验证后的结构化 plan、提示、示意鞋、匹配级别、解释和来源 | design_result.plan_provenance（沿用内部输出 schemaVersion=1） | 白名单投影给前端，不直接公开整个 JSON；IMAGE_ONLY 原样复制业务内容 |
| 输出与输入文件 | design_task_asset | OUTPUT 仅在可靠保存后绑定，新增引用沿用锁顺序和清理规则 |
| 无方案失败的结构化原因、阶段、类别 | 新增 design_task.outcome_snapshot JSON NULL | NO_MATCH 无 design_result，不把失败写进不可变 input_snapshot 或供应商诊断字段 |

本轮 V3 只新增 outcome_snapshot 一列，不新增表；列内保存 schemaVersion=1、category、stage、code、message、suggestedAction，不保存完整原始模型响应。任务状态、错误字段、outcome_snapshot、名额释放同事务提交。成功时 outcome_snapshot 清空；UNKNOWN 转入可恢复阶段时同步清理过期错误视图。旧任务该列为 null，按已有 errorCode/errorMessage 投影，不伪造过去的判定原因。

design_type 为 VARCHAR(16)，OVERALL 能容纳，现有 SQL 无模式 CHECK；无需仅为枚举扩大列。但须扩展应用验证、列表筛选、前端标签、固定明细适用性和重试规则，不能宣称数据库能存就代表整体设计已支持。若更新列注释，放入后续迁移，不改 V1。

迁移使用 V3__design_generation_outcome.sql，由 ops 显式执行，应用启动检查 outcome_snapshot 与所需 JSON schema 支持。前后端配套发布，旧页面不能静默提交旧结构；目前没有已发布的提交写接口消费者，但现有只读页面必须验证新增模式和字段。回退前评估旧应用不识别 OVERALL/新快照的问题，不能仅凭新增列可空认定可安全回滚。
