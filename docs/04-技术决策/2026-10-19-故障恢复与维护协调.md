# 图片处理、故障恢复与维护协调

最后整理：2026-10-20。决策日期沿用原记录；未实施或运行验证。

本记录的备份部分已由 [表命名与范围调整](2026-10-19-表命名与备份范围调整.md) 暂缓；其余决定按当前架构执行。
日期：2026-10-19。状态：设计方向已确认，尚未实施或演练。

## 背景

架构检查发现，七牛直传后的处理职责、模型结果暂存、旧模型配置查找、备份协调及依赖故障行为尚未闭环。用户确认按检查建议补齐，不新增独立服务。

## 原决定与当前适用范围

- server 后台处理图片，客户端通知与后台定期核查共同触发核验；状态与执行权持久化，原图、处理图、缩略图分别追踪。
- 模型结果先可靠保存到 server 自己的持久化暂存目录，再上传七牛并入库，成功后清理暂存。暂存跨容器重建保留，替代不了七牛长期存储。
- 只有已可靠保存或供应商可重新获取的结果才能恢复保存；响应尚未可靠保存就丢失的窗口不能承诺完全恢复，也不能自动重发生图。
- server/config/ 保存版本化模型配置，任务按原版本加载，凭据独立引用。旧任务仍需要的配置保留，缺失时明确阻止执行。
- ops 一次性任务协调维护与备份（备份已暂缓，维护持久化方式待讨论），server 执行维护状态；内部控制必须鉴权，普通业务接口不提供该能力。
- 【已暂缓的历史决定】备份保护清单中的不可变对象，复制校验完成后才释放清理保护。未确认入库的直传对象不属于本批次业务快照。备份中断保留恢复状态。
- MySQL 故障停止依赖数据库的业务与任务领取；Redis 故障拒绝需鉴权请求；七牛故障保留待处理状态和暂存；模型故障仅影响生成流程。健康检查区分存活和依赖可用性。

## 取舍与验收

以上机制仍在现有 server 与 ops 内实现，增加必要的持久状态和临时磁盘需求。跨数据库、云存储、外部模型的操作不具备单一事务保证，依靠可恢复步骤、幂等写入和状态核实处理。

后续实施需演练：浏览器直传完成后关闭、核验进程中断、模型返回后七牛失败、保存期间重启、旧配置缺失及依赖服务不可用。原有“备份期间删除对象”演练随备份方案暂缓；当前没有执行上述验证。
