# 执行隔离、容量控制与统一异常处理

最后整理：2026-10-20。决策日期沿用原记录；未实施或运行验证。

日期：2026-10-19。

状态：执行池划分、初始并发、调度原则及可配置范围已于 2026-10-20 确认；未定容量数值、准入实现和字段方案仍按相关草案审阅，尚未实施或验证。

## 背景

模型调用、图片核验、结果保存耗时不同，共用执行资源会相互阻塞。仅限制并发不能限制积压；多设备编辑可能覆盖新值。用户明确要求通过运行时异常和统一异常处理向前端返回错误。

## 决定

- 保留单进程架构，后台工作使用隔离、有界的执行资源，数据库保存待处理任务。容量不足时拒绝新增工作，保留已接收工作。
- 可编辑资料、衣物和收藏夹名称采用版本校验，冲突返回 409 并保留用户输入。不可变历史和任务执行权沿用各自规则。
- 业务异常继承 RuntimeException，在统一 HTTP 出口映射为状态码及稳定错误结构。过滤器失败使用同一格式；未知异常不暴露内部细节。
- 后台异常由执行器边界处理并持久化阶段状态，不依赖 HTTP 异常处理器，也不将超时一律认定为失败。

2026-10-20 补充确认：默认最多 2 个活动设计任务，衣物识别默认并发 1；识别与规划共享 DeepSeek 供应商总并发额度，规划优先并保证识别有执行机会，不中断已发出的请求。图片处理、结果保存和清理使用独立执行资源；保存优先，清理默认单路低并发。并发、调度参数、队列及容量阈值均可配置，具体范围见架构设计。上述初值是实施起点，不代表已验证的承载能力。

## 理由与影响

执行隔离让模型等待不会耗尽图片处理或保存线程。准入限制使积压有边界；版本校验避免静默覆盖。统一异常出口避免 Controller 重复处理，保持事务回滚与前端错误契约一致。

需要实现容量检查、执行槽释放、版本条件更新及异常映射，并验证失败状态不会随原事务回滚。线程池和队列虽独立，数据库连接、内存和磁盘仍需共同预算。

本轮未逐一评估新的消息队列、微服务或通用工作流方案；沿用已确认的首版单进程边界。已确认的池划分与初值尚未运行验证，其余容量数值和字段范围继续按相关草案审阅。
