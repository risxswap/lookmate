# 上传图片核验失败

日期：2026-10-23。状态：已使用 Thumbnailator 修复 JPEG 误判并完成本机验证；运行中的开发服务尚未重启。

## 已观察到的现象

用户上传图片后看到“图片已失效，请移除后重新选择”，服务端没有对应日志。

通过 Chrome 开发者工具读取当前个人照片页面：

- 文件名为 `PA170045.JPG`。
- 上传授权返回 201，七牛上传返回 200，`/api/files/2/complete` 返回 202。
- 最后一次 `GET /api/files/2` 返回 200，业务状态为 `REJECTED`，`validationError` 为“不支持动态图片”。请求标识为 `e37ba772-724b-45c5-bf22-f188ea7c1275`。
- 控制台还存在 `/api/files/1` 的 404，但该请求的响应正文已不在 Network 记录中，不能把它与文件 2 的失败直接等同。

## 代码检查与对照实验

`ImageProcessor.process` 在读取尺寸后，以 `reader.getNumImages(true) != 1` 判断“不支持动态图片”。此外，APNG 和 WebP 动画标识也会触发这一提示。尚未取得原图，不能确认它具体触发哪一分支。

在本机 Java 21.0.8 的 JShell 中使用 ImageIO 生成 20×20 静态 JPEG，并按当前代码顺序设置 reader、读取宽高及图片数量：

- 单张 JPEG：JDK `JPEGImageReader` 返回 `images=1`。
- 将两份静态 JPEG 字节依次放入同一数据流：返回 `images=2`，且 `reader.read(0)` 成功。

这证明图片数量不为 1 不能单独证明文件是动态图。实验仅验证判断条件，不证明用户原图包含多个 JPEG，也未构造或验证 MPO 文件。

`FileService` 捕获 `InvalidImageException` 后只更新数据库，没有记录拒绝日志。`ApiExceptionHandler` 返回业务 404 时也没有日志。因此没有服务端日志与当前实现一致，不能据此判断请求没到后端。

`FileMapper.reject` 将失败图片的 `cleanup_after` 设为当前时间，后续清理可删除记录。前端将状态查询的 404 统一转换为“图片已失效”。这存在失败原因被清理流程掩盖的可能，但文件 1 是否经过这一过程尚无运行证据。

## 后续验证与建议

用户提供目录后，在外置数据卷的图片目录找到原图，并使用 Java 21.0.8 的 JDK JPEGImageReader 按业务代码顺序检查：

- 文件大小 9,835,471 字节，格式 JPEG，主图 5184×3888，共 20,155,392 像素，均在上传限制内。
- `getNumImages(true)` 返回 2，`read(0)` 正常解码主图。
- 尝试读取第二张图的尺寸失败：`Not a JPEG file: starts with 0x67 0x66`。
- 按 JPEG 标记和段长度检查，主图结束位置为字节偏移 9,692,426，后面还有 143,045 字节，起始字节为 `67 66`。文件内未发现 MPF 标记；不能将其描述为已确认的 MPO。
- 只在内存中保留主 JPEG 至结束标记的字节，再执行相同尺寸和图片数量检查，得到 `images=1`，主图解码成功。原文件未改动。

原图实验确认：尾随数据使当前解码器报告了额外图片，代码再将图片数量不为 1 解释成动态图，导致本次拒绝。尾随数据的来源及用途尚未确定。本轮验证了原图及触发判断，未运行完整存储上传链路的修复回归。

建议 JPEG 以主图能否完整解码作为有效性检查的一部分，不用通用图片计数断言它是动画；保留 PNG/WebP 的动画标记检查及大小、像素限制。另需补充核验拒绝日志，并避免失败原因在前端读取前被清理。以上均为建议，尚未实施或验证修复。
