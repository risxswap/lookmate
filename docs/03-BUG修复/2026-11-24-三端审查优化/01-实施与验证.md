| 路径 | 审查项 | 实施结果 |
| --- | --- | --- |
| 图片引用与清理 | R1 | 在账号锁内统一核对直接引用与衣物识别快照。仍属本人衣橱的历史误标图片可继续用于设计。清理器分批扫描并重访暂时受阻的文件，删除前再次核验引用。 |

| 小程序列表与首页 | R3、R4 | 仅已应用的筛选条件参与翻页，失败后保留已加载数据。首页逐张处理封面失败。日期操作只读安排，活动任务轮询只读工作台。补测了切换日期请求在途时隐藏后返回，以及此期间切换账号。 |

## MySQL 实测

在独立 MySQL 8.0.45 上分别运行基线与优化后的实际 Service，通过同一连接的 session status 读取每次操作的 SQL 计数。使用相同合成数据、关闭后台干扰并清空当前 MyBatis 会话查询缓存。计数不含准备数据及核对结果的操作。

| 场景 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 常用搭配列表第 1 页，20 套，无分组筛选 | 62 次 SELECT | 5 次 SELECT |
| 日历当天第 1 页，5 套不同搭配，每套 8 件不同衣物 | 47 次 SELECT | 4 次 SELECT |
| 生成候选的衣橱读取，40 件衣物各 1 张图 | 45 次 SELECT | 6 次 SELECT |
| 8 件衣物、1 个分组的搭配只改名，仍发送原有单品和分组 | 3 次 DELETE、17 次 INSERT、9 次 UPDATE | 仅 1 次 UPDATE |

搭配分页和总数仍由服务端返回，日历名称和图片仍取历史快照。候选选取后的文件引用保留锁内复核。以上读数对应给定数据与调用范围，未测生产响应时间。

日常释放文件时，在账号锁内用一条 SQL 依次检查引用是否存在。隔离库为 800 个账号各准备了 1 套搭配。`EXPLAIN ANALYZE` 显示，仅搭配来源图匹配时，通过 `idx_outfit_user_pinned` 找到本账号的 1 行。个人照片先命中时，末尾的搭配查询未执行。后台删除前仍要检查跨账号的异常引用，这一步如果前面均未命中，仍可能扫描搭配表。本次沿用既有索引。
